# Концепция и фичи телеграм-бота для системных встреч дружеской компании

## 1. Проблема

Со временем участники дружеской компании постепенно "отваливаются" — учёба, работа,
отношения забирают всё внимание, и живое общение сходит на нет без злого умысла
с чьей-либо стороны, просто по инерции. Раньше это решалось вручную: раз в 2 недели
назначалась пара ответственных, которая опрашивала всех, согласовывала время и место
и организовывала встречу. Схема работала, но держалась на энтузиазме конкретных людей
и не масштабировалась.

**Цель проекта** — сделать встречи компании системными за счёт бота: снять с людей
рутину организации, но и не дать пропускам стать привычкой — бот должен вовремя
напоминать тем, кто давно не был на встречах.

Бот — дополнение к основному групповому чату (с топиками), а не его замена: правила,
опросы и флуд остаются в чате, бот берёт на себя организационный слой.

## 2. Терминология

- **Проект** — отдельная компания/комьюнити со своим Telegram-чатом, изолированным
  реестром участников и своими настройками бота. Бот проектируется как мультитенантный:
  один бот может обслуживать множество независимых проектов одновременно.
- **Мероприятие** — конкретная встреча внутри проекта. В рамках одного проекта может быть
  несколько активных мероприятий параллельно.
- **Сбор** — сбор денег на общую покупку в рамках проекта (пицца, аренда места и т.п.).

## 3. Ключевые архитектурные решения

- **Мультитенантность заложена с самого начала** на уровне модели данных (реестр
  участников, мероприятия, сборы, настройки — всё изолировано по проекту), но полноценный
  self-service мастер создания нового проекта чужим админом — не в MVP. Подключение новых
  компаний на первых порах делается вручную/полутехнически. Продукт архитектурно готов
  к переиспользованию другими компаниями, но без коммерческих обязательств на старте
  (без биллинга, без публичного релиза).
- **Один Telegram-аккаунт может состоять в нескольких проектах** одновременно, статистика
  и напоминания ведутся раздельно по каждому проекту.
- **Регистрация вместо чтения списка участников чата.** Telegram Bot API не позволяет
  боту получить полный список участников группы. Поэтому бот ведёт собственный реестр:
  человек регистрируется один раз через deep-link-кнопку (`t.me/bot?start=project_id`)
  в посте чата (закрепляет его вручную администратор) — это переводит его в ЛС и
  одновременно даёт боту право
  присылать личные уведомления. Без регистрации тег по @username всё ещё может сработать
  (если ник публичный), но ЛС-уведомления и трекинг посещаемости — не работают.
- **Web App (Telegram Mini App)** используется везде, где нужна форма с несколькими
  полями и/или выбор нескольких людей из списка: создание мероприятия, создание сбора,
  постфактум-отметка явки. Простые одиночные да/нет-действия (RSVP, подтверждение оплаты)
  остаются обычными inline-кнопками бота — не требуют Web App.
  Важный нюанс: Web App может технически опознать пользователя даже без прохождения
  deep-link регистрации, но это не даёт бота права писать ему в ЛС — интерфейс должен
  явно предупреждать об этом и предлагать пройти регистрацию.
- **Постоянная точка входа в Web App — кнопка-меню бота в личке.** Помимо команд
  под конкретную задачу (`/new_event` и т.п.), у бота в приватном чате всегда есть
  встроенная кнопка-меню, открывающая **домашний экран** Web App: кто пользователь,
  в каком проекте, и переходы на доступные действия. В MVP это навигационный хаб
  без статистики посещаемости (сама статистика/геймификация — backlog, раздел 5).
- **Мероприятие может быть без организатора.** Для лёгких, не требующих подготовки
  встреч (вечерняя прогулка и т.п.) создатель мероприятия может не назначать
  со-организатором ни себя, ни кого-либо ещё. У мероприятия без организатора право
  редактировать/отменять его и постфактум поправить чужой RSVP переходит к создателю
  мероприятия и админам проекта — специального "хозяина" мероприятия в этом случае нет.
- **RSVP — одновременно намерение и факт.** Отдельного постфактум-шага "отметить явку"
  нет: кнопки "участвую"/"не участвую" под анонсом — это и намерение прийти, и (после
  того как мероприятие состоялось) единственный источник данных о том, кто реально был.
  Организатор (а если его нет — создатель мероприятия) и админ проекта могут поправить
  чужой статус RSVP постфактум — это предусмотренный способ скорректировать ошибочную
  самоотметку. Таймер "давно не виделись" сбрасывается по списку подтвердивших участие
  не сразу, а в полночь следующего дня после окончания мероприятия — без привязки к
  точному времени, чтобы оставить запас на правки.

## 4. MVP — функциональность

### 4.1 Регистрация и участники
- Закреплённый пост в чате с deep-link-кнопкой — разовая регистрация человека в проекте.
- Удаление человека из реестра — только вручную админом (человек может выйти из группы
  "по приколу" и вернуться — авто-удаление по событию выхода из чата не делаем).
- Админ проекта — тот, кто добавил бота (может назначать со-админов). Права админа:
  настройки проекта (пороги напоминаний/эскалации), модерация реестра и мероприятий.
  Споры по сборам — вне зоны ответственности админа, регулируются людьми напрямую.

### 4.2 Тегание
- Команда `/all` в группе — тегает разом всех зарегистрированных участников проекта.
- Точечный выбор части людей (для формы мероприятия или сбора) — чекбоксами в Web App.

### 4.3 Мероприятия
- Создаются через Web App: дата и время начала, место, описание — обязательные поля;
  дата/время окончания (для мероприятий на несколько дней), бюджет с человека и лимит
  мест — опциональные. Набор полей расширяемый на будущее.
- Лимит мест — «мягкий»: это ориентир, сколько человек нужно собрать, чтобы
  мероприятие состоялось, а не жёсткий потолок. По достижении лимита кнопки RSVP
  продолжают работать, счётчик подтвердивших становится условным (например,
  «17/15») с пометкой, что цель набрана.
- Создать может любой участник проекта (без технического ограничения по роли).
- Поддержка нескольких равноправных **со-организаторов** на одно мероприятие
  (редактируют мероприятие, постфактум корректируют чужой RSVP, получают
  напоминания) — прямое продолжение исходной механики "ответственной пары". Со-
  организаторов может не быть вовсе (создатель вправе снять чекбокс и с себя) —
  см. раздел 3, "мероприятие может быть без организатора".
- Публикация анонса в чат с простыми inline-кнопками "участвую/не участвую". Анонс
  живо обновляется при каждом нажатии: в самом сообщении пересчитываются счётчик
  подтвердивших и два списка никнеймов — кто участвует и кто отказался. Третья
  группа (кто ещё не нажал ни одну кнопку — «не прочитал / думает») в анонсе
  отдельно не выводится, она видна как «все остальные из реестра». Участники видят
  актуальную картину, не открывая ничего дополнительно.
- Несколько мероприятий могут быть активны параллельно.
- Редактирование и отмена мероприятия — организатором (либо создателем/админом, если
  организатора нет), с уведомлением всех, кто уже подтвердил участие.

### 4.4 Учёт посещаемости и напоминания
- Отдельного постфактум-шага "отметить явку" нет (см. раздел 3): факт явки — это
  список подтвердивших RSVP на момент запуска таймера. Организатор (или создатель/
  админ, если организатора нет) может постфактум поправить чужой статус RSVP, если
  кто-то отметился неверно.
- Таймер "давно не виделись" по каждому подтвердившему сбрасывается не сразу после
  мероприятия, а в полночь следующего дня после его окончания — это и есть встроенный
  запас времени на правки RSVP, отдельное напоминание "заполните чек-лист" не нужно.
- Личное напоминание "ты уже N дней не виделся с друзьями, ближайшее мероприятие..." —
  приватное сообщение в ЛС. Порог N дней — настраиваемый параметр проекта (задаёт админ).
- Если человек пропустил подряд M мероприятий (по умолчанию 3, настраивается админом) —
  бот прекращает слать ему то же самое напоминание и вместо этого уведомляет организатора
  (или, если организатора нет, админа проекта) лично, передавая инициативу живому человеку.
- Статистика посещаемости приватна: публичного рейтинга/лидерборда нет.

## 5. Пост-MVP / следующий релиз (backlog)

- **Сбор денег на общую покупку**:
  - Создать сбор может любой участник проекта.
  - Возможность создать сбор **привязанным к уже существующему мероприятию**
    (а не только как отдельная самостоятельная сущность).
  - Выбор участников сбора — чекбоксами (аналогично выбору для мероприятия).
  - Сумма делится поровну по умолчанию, с возможностью вручную скорректировать
    сумму на конкретного человека.
  - Реквизиты для перевода (банк/номер) сохраняются в профиль создателя, предлагаются
    выпадающим списком, редактируемы перед отправкой.
  - Уведомление о сборе с реквизитами и кнопкой подтверждения — в ЛС или в группу,
    канал выбирает создатель сбора при создании.
  - Подтверждение — участник жмёт кнопку "оплатил" (на доверии, без проверки).
    Создатель сбора видит список подтвердивших и вручную улаживает расхождения
    (например, пишет в ЛС тому, кто не подтвердил).
  - Редактирование и отмена сбора — с уведомлением всех участников сбора.
- **Прикрепление изображений** к формам мероприятия и сбора (например, фото места,
  фото чека/покупки как подтверждение).
- **Опрос впечатлений** после мероприятия (плюсы/минусы прошедшей встречи) — отдельная
  фича, не связана с трекингом посещаемости и не заменяет постфактум-отметку явки.
- **Режим паузы/отпуска** — команда, временно отключающая личные напоминания конкретному
  человеку (уехал, сессия, декрет и т.п.), без исключения из тегов на общие опросы.
- **Личный кабинет** — статистика посещений, геймификация. Раздел домашнего экрана
  Web App, который сам по себе (как навигационный хаб) входит в MVP, — backlog
  здесь именно статистика и геймификация.
- **Автоматизация ротации ответственных** — бот сам назначает очередь организаторов
  вместо ручного расписания.
- **Полноценный self-service онбординг** новых проектов для чужих админов (создание
  проекта без участия разработчика).

## 6. Явно вне рамок MVP (сознательное решение)

- Публичная статистика/геймификация посещаемости.
- Автоматическое исключение из реестра при выходе из группового чата.
- Коммерциализация (биллинг, публичный релиз для незнакомых пользователей).
- Проверка/валидация факта оплаты в сборах (эта фича и в релизе остаётся на доверии).
