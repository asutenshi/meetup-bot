# Подзадачи реализации

Разбивка укрупнённых этапов из [`TZ.md`, раздел 7](./TZ.md#7-этапы-реализации-roadmap)
на подзадачи PR-размера. Каждый пункт — одна ветка, один PR (см. правила в
корневом [`CLAUDE.md`](../CLAUDE.md)). Ссылки в скобках — на разделы `TZ.md`/
`CONCEPT.md` с деталями реализации конкретного пункта.

Отмечать пункт `- [x]` в том же PR, который его закрывает.

## Этап 1. Реестр участников и мультитенантный каркас

- [x] **1.1 Модели и миграции БД.** SQLAlchemy 2.0 async модели `Project`,
      `ProjectTopicSetting`, `ProjectSettings`, `User`, `ProjectMembership`;
      Alembic init + первая миграция. (TZ §2.1–2.5)
- [x] **1.2 Каркас приложения.** Конфиг через `pydantic-settings`, асинхронная
      сессия БД, точка входа режима `bot+api` (aiogram + FastAPI на одном
      ASGI/uvicorn), `GET /health`. (TZ §3.1, §6.2)
- [x] **1.3 Создание проекта при добавлении бота.** Хендлер `my_chat_member` →
      создание `Project`/`ProjectSettings`/первого `User`+`ProjectMembership(admin)`.
      (TZ §3.3, шаг 2)
- [x] **1.4 `/setup_registration`.** Идемпотентный вызов внутри топика →
      сохранение `Project.default_thread_id`; создание `Project`, если ещё нет
      (общий путь с 1.3). (TZ §3.3, шаг 1; §3.5)
- [x] **1.5 Пост регистрации.** Публикация сообщения с inline URL-кнопкой
      `t.me/<bot>?start=<invite_payload>` в нужный топик и напоминания
      закрепить его вручную, сохранение `pinned_message_id`; закрепление и
      открепление (в т.ч. старого поста при переносе топика) — полностью на
      ответственности администратора чата, бот их не выполняет.
      (TZ §3.3, шаг 3; §4.1)
- [x] **1.6 `/start` и регистрация участника.** Парсинг `invite_payload`, upsert
      `User`/`ProjectMembership(member)`, приветственное сообщение;
      `/start` без payload — подсказка. (TZ §3.3, шаги 4–5; §4.1)
- [x] **1.7 `/all`.** Сбор упоминаний активных участников (`@username` или
      text-mention), разбивка на несколько сообщений при превышении лимита
      длины, троттлинг. (TZ §4.2; §6.1 rate limiting)
- [ ] **1.8 Админ-команды реестра.** `/members`, удаление участника
      (`status=removed`, `removed_by`/`removed_at`), `/add_admin` — с проверкой
      `role=admin` на бэкенде. (TZ §4.1; §6.1 права ролей)
- [ ] **1.9 `/set_topic`.** Привязка топика к категории (`events` /
      `money_collections` / `general`) через upsert `ProjectTopicSetting`,
      функция `resolve_thread_id(project_id, category)` для дальнейшего
      переиспользования. (TZ §3.5)

## Этап 2. Мероприятия: создание и RSVP

- [ ] **2.1 Каркас Web App.** Vite + React + TypeScript, `@telegram-apps/sdk`,
      `@telegram-apps/telegram-ui`, раздача статики; генерация TS-типов из
      OpenAPI (`openapi-typescript`). (TZ §1.2 таблица «Web App фронтенд»)
- [ ] **2.2 Валидация `initData` на бэкенде.** Проверка `hash` (HMAC,
      `hmac.compare_digest`), `auth_date`, извлечение `tg_user_id`; FastAPI
      dependency, переиспользуемая всеми `/api/*`. (TZ §3.2)
- [ ] **2.3 Модели `Event`, `EventCoOrganizer`, `EventRSVP` + миграция.**
      (TZ §2.6–2.8)
- [ ] **2.4 Форма создания мероприятия + `POST /api/events`.** Поля из TZ §4.3
      п.2, создание `Event`+`EventCoOrganizer`, публикация анонса в топик
      категории `events` с кнопками «Участвую»/«Не участвую»,
      `announcement_message_id`. (TZ §3.5; §4.3)
- [ ] **2.5 Обработка RSVP.** Callback-хендлер upsert `EventRSVP`, обновление
      счётчика/текста под кнопками. (TZ §4.3 «RSVP»)
- [ ] **2.6 Редактирование мероприятия.** Web App-форма с предзаполнением,
      проверка `EventCoOrganizer` при открытии/сохранении, `editMessageText`
      анонса, личные уведомления подтвердившим. (TZ §4.3 «Редактирование/отмена»)
- [ ] **2.7 Отмена мероприятия.** `status=cancelled`, пометка анонса,
      уведомление подтвердивших. (TZ §4.3 «Редактирование/отмена»)

## Этап 3. Постфактум-отметка явки

- [ ] **3.1 Модель `EventAttendance` + миграция.** (TZ §2.9)
- [ ] **3.2 Web App-форма чек-листа явки.** Список RSVP=going с чекбоксами +
      ручное добавление пришедших без RSVP. (TZ §4.4 п.1)
- [ ] **3.3 `POST /api/events/:id/attendance`.** Массовая запись
      `EventAttendance`, `attendance_checklist_filled_at`, пересчёт
      `last_attended_at`/`consecutive_missed_events` на затронутых
      `ProjectMembership`. (TZ §3.4 последний абзац; §4.4 п.2)

## Этап 4. Напоминания и эскалация

- [ ] **4.1 Worker-процесс.** Отдельная точка входа режима `worker`,
      APScheduler, периодический проход (15–30 мин), второй сервис в
      `docker-compose.yml` из того же образа. (TZ §1.2 таблица «Планировщик»;
      §3.1 п.1)
- [ ] **4.2 Джоба: напоминание организатору о незаполненном чек-листе.**
      (TZ §3.4 п.1)
- [ ] **4.3 Джоба: личное напоминание участнику «давно не виделись».**
      Троттлинг раз в день. (TZ §3.4 п.2)
- [ ] **4.4 Джоба: эскалация организатору/админу.** Троттлинг раз в период.
      (TZ §3.4 п.3)
- [ ] **4.5 Настройка порогов `ProjectSettings`.** Минимальный UI/команды для
      админа (`reminder_days_threshold`, `unfilled_checklist_hours`,
      `missed_events_escalation_count`, `timezone`). (TZ §2.3; roadmap §7
      Этап 4)

## Этап 5. Полировка

- [ ] **5.1 Граничные случаи.** Бот заблокирован пользователем (`403`, пометка
      на `User`/`ProjectMembership`), повторные клики по RSVP, пустые
      мероприятия при закрытии чек-листа, гонки при одновременном
      редактировании. (TZ §6.2; roadmap §7 Этап 5)
- [ ] **5.2 Логирование.** Структурированные JSON-логи в stdout, ротация через
      Docker, обязательные события из §6.2. (TZ §6.2)
- [ ] **5.3 Бэкапы.** Ежедневный `pg_dump` по cron, хранение N копий локально +
      выгрузка во внешнее хранилище. (TZ §6.3)
- [ ] **5.4 Прод-деплой.** Docker Compose (домашний Proxmox + Tailscale
      Funnel), настройка TLS/ingress, финальная сверка health-check. (TZ §1.3
      вариант А; §6.2)
