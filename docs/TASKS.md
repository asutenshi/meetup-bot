# Подзадачи реализации

Разбивка укрупнённых этапов из [`TZ.md`, раздел 7](./TZ.md#7-этапы-реализации-roadmap)
на подзадачи PR-размера. Каждый пункт — одна ветка, один PR (см. правила в
корневом [`CLAUDE.md`](../CLAUDE.md)). Ссылки в скобках — на разделы `TZ.md`/
`CONCEPT.md` с деталями реализации конкретного пункта.

Отмечать пункт `- [x]` в том же PR, который его закрывает.

## Этап 1. Реестр участников и мультитенантный каркас

- [x] **1.1 Модели и миграции БД.** SQLAlchemy 2.0 async модели `Project`,
      `ProjectTopicSetting`, `ProjectSettings`, `User`, `ProjectMembership`;
      Alembic init + первая миграция. (TZ §2.1–2.5)
- [x] **1.2 Каркас приложения.** Конфиг через `pydantic-settings`, асинхронная
      сессия БД, точка входа режима `bot+api` (aiogram + FastAPI на одном
      ASGI/uvicorn), `GET /health`. (TZ §3.1, §6.2)
- [x] **1.3 Создание проекта при добавлении бота.** Хендлер `my_chat_member` →
      создание `Project`/`ProjectSettings`/первого `User`+`ProjectMembership(admin)`.
      (TZ §3.3, шаг 2)
- [x] **1.4 `/setup_registration`.** Идемпотентный вызов внутри топика →
      сохранение `Project.default_thread_id`; создание `Project`, если ещё нет
      (общий путь с 1.3). (TZ §3.3, шаг 1; §3.5)
- [x] **1.5 Пост регистрации.** Публикация сообщения с inline URL-кнопкой
      `t.me/<bot>?start=<invite_payload>` в нужный топик и напоминания
      закрепить его вручную, сохранение `pinned_message_id`; закрепление и
      открепление (в т.ч. старого поста при переносе топика) — полностью на
      ответственности администратора чата, бот их не выполняет.
      (TZ §3.3, шаг 3; §4.1)
- [x] **1.6 `/start` и регистрация участника.** Парсинг `invite_payload`, upsert
      `User`/`ProjectMembership(member)`, приветственное сообщение;
      `/start` без payload — подсказка. (TZ §3.3, шаги 4–5; §4.1)
- [x] **1.7 `/all`.** Сбор упоминаний активных участников (`@username` или
      text-mention), разбивка на несколько сообщений при превышении лимита
      длины, троттлинг. (TZ §4.2; §6.1 rate limiting)
- [x] **1.8 Админ-команды реестра.** `/members`, удаление участника
      (`status=removed`, `removed_by`/`removed_at`), `/add_admin` — с проверкой
      `role=admin` на бэкенде. (TZ §4.1; §6.1 права ролей)
- [x] **1.9 `/set_topic`.** Привязка топика к категории (`events` /
      `money_collections` / `general`) через upsert `ProjectTopicSetting`,
      функция `resolve_thread_id(project_id, category)` для дальнейшего
      переиспользования. (TZ §3.5)
- [x] **1.10 Меню команд бота (`setMyCommands`).** Регистрация подсказок команд
      по `/` через `bot.set_my_commands()` при старте приложения, отдельно для
      `BotCommandScopeAllPrivateChats` (`/start`) и
      `BotCommandScopeAllGroupChats` (`/setup_registration`, `/set_topic`,
      `/all`, `/members`, `/remove_member`, `/add_admin`). (TZ §3.6)
- [ ] **1.11 Топик регулирования прав (`rights`) и гейт admin-команд.** Категория
      `TopicCategory.RIGHTS` в `/set_topic`/`/unset_topic`; новая команда
      `/remove_admin` (понижение `role=admin` → `role=member`, только `role=owner`,
      инлайн-выбор → подтверждение, симметрично `/add_admin`); гейт по топику
      `rights` для `/members`, `/remove_member`, `/add_admin`, `/remove_admin` с
      fallback, если топик не назначен или чат без топиков. (TZ §2.2, §3.5, §3.7,
      §4.1)

## Этап 2. Мероприятия: создание и RSVP

- [x] **2.1 Каркас Web App.** Vite + React + TypeScript, `@telegram-apps/sdk`,
      `@telegram-apps/telegram-ui`, раздача статики; генерация TS-типов из
      OpenAPI (`openapi-typescript`). Заложить визуальный язык из
      [`WEBAPP_DESIGN.md`](./WEBAPP_DESIGN.md): семантические токены на
      `themeParams`, акцентный цвет — одним сменяемым токеном `--accent`
      (финальный цвет пока не выбран), без хардкода акцента в компонентах.
      (TZ §1.2 таблица «Web App фронтенд»)
- [ ] **2.2 Валидация `initData` на бэкенде.** Проверка `hash` (HMAC,
      `hmac.compare_digest`), `auth_date`, извлечение `tg_user_id`; FastAPI
      dependency, переиспользуемая всеми `/api/*`. (TZ §3.2)
- [ ] **2.3 Модели `Event`, `EventCoOrganizer`, `EventRSVP` + миграция.**
      Включая `Event.ends_at`, `Event.attendance_finalized_at`,
      `EventRSVP.updated_by`. (TZ §2.6–2.8)
- [ ] **2.4 Форма создания мероприятия + `POST /api/events`.** Поля из TZ §4.3
      п.2 (в т.ч. опциональный `ends_at`, со-организаторы — от нуля и больше,
      создатель может снять чекбокс и с себя), создание `Event`+
      `EventCoOrganizer`, публикация анонса в топик категории `events` с
      кнопками «Участвую»/«Не участвую», `announcement_message_id`.
      (TZ §3.5; §4.3)
- [ ] **2.5 Обработка RSVP + живое обновление анонса.** Callback-хендлер
      upsert `EventRSVP` (`updated_by = user_id`), `editMessageText` анонса с
      пересчётом счётчика и списка никнеймов подтвердивших при каждом
      нажатии. (TZ §4.3 «RSVP»)
- [ ] **2.6 Редактирование мероприятия.** Web App-форма с предзаполнением,
      проверка прав при открытии/сохранении (`EventCoOrganizer`, либо, если
      таких строк нет, `created_by`/`role=admin`), `editMessageText` анонса,
      личные уведомления подтвердившим. (TZ §4.3 «Редактирование/отмена»)
- [ ] **2.7 Отмена мероприятия.** `status=cancelled`, пометка анонса,
      уведомление подтвердивших. (TZ §4.3 «Редактирование/отмена»)

## Этап 3. Постфактум-корректировка RSVP

- [ ] **3.1 Экран корректировки RSVP.** Список участников проекта с текущим
      статусом RSVP по мероприятию, доступен организатору/со-организатору
      (либо создателю/админу, если организатора нет); переиспользует
      компонент выбора людей (TZ §4.2). (TZ §4.4 «Постфактум-корректировка
      RSVP» п.1)
- [ ] **3.2 Эндпоинт корректировки чужого RSVP.** Upsert `EventRSVP` с
      `updated_by`, отличным от `user_id`; проверка прав по тому же правилу,
      что в 2.6; до финализации — просто меняет статус (и анонс), после
      финализации — точечно пересчитывает `last_attended_at`/
      `consecutive_missed_events` скорректированного участника. (TZ §3.4 п.1
      последний абзац; §4.4 «Постфактум-корректировка RSVP» п.2)

## Этап 4. Напоминания, финализация явки и эскалация

- [ ] **4.1 Worker-процесс.** Отдельная точка входа режима `worker`,
      APScheduler, периодический проход (15–30 мин), второй сервис в
      `docker-compose.yml` из того же образа. (TZ §1.2 таблица «Планировщик»;
      §3.1 п.1)
- [ ] **4.2 Джоба: финализация явки по списку RSVP.** В полночь следующего
      дня после `ends_at`/`starts_at` (таймзона проекта) — факт явки из
      текущего `EventRSVP`, сброс `last_attended_at`/`consecutive_missed_events`,
      простановка `Event.attendance_finalized_at`. (TZ §3.4 п.1)
- [ ] **4.3 Джоба: личное напоминание участнику «давно не виделись».**
      Троттлинг раз в день. (TZ §3.4 п.2)
- [ ] **4.4 Джоба: эскалация организатору/админу.** Троттлинг раз в период.
      (TZ §3.4 п.3)
- [ ] **4.5 Настройка порогов `ProjectSettings`.** Минимальный UI/команды для
      админа (`reminder_days_threshold`, `missed_events_escalation_count`,
      `timezone`). (TZ §2.3; roadmap §7 Этап 4)

## Технический долг

- [x] **Ревью админ-команд реестра скиллом `/grill-me`.** Пройтись по
      `/members`, `/remove_member`, `/add_admin` и логике ролей
      (`owner`/`admin`/`member`, см. 1.8) — реализация шла быстрой итерацией,
      и уже по ходу работы нашлись два бага (реактивация удалённого участника
      при повторном `/start`, отсутствие защиты владельца от удаления и от
      неконтролируемого назначения новых админов). Сигнал стресс-тестировать
      эту область целенаправленно, а не полагаться только на обычное ревью.
      Результат ревью — топик `rights` и гейт admin-команд (1.11), новые
      команды `/unset_topic`/`/remove_admin`, зафиксированный пробел
      `/transfer_owner` (TZ §5).

- [ ] **`/set_topic`: порядок проверок вводит не-админа в заблуждение.**
      В `src/meetup_bot/bot/handlers/set_topic.py` валидация категории стоит
      раньше проверки роли. Если не-админ вызывает `/set_topic` без категории
      (или с некорректной), бот отвечает «Укажите категорию после команды…»,
      хотя настоящая причина отказа — отсутствие прав. Указав корректную
      категорию, тот же пользователь получит уже «Эту команду может вызвать
      только администратор проекта». Починка: проверять существование проекта
      и `role=admin` раньше разбора аргументов (порядок как в 1.11 при добавлении
      категории `rights`). Симметрично проверить `/unset_topic`. (TZ §3.5)
