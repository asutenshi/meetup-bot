# Подзадачи реализации

Разбивка укрупнённых этапов из [`TZ.md`, раздел 7](./TZ.md#7-этапы-реализации-roadmap)
на подзадачи PR-размера. Каждый пункт — одна ветка, один PR (см. правила в
корневом [`CLAUDE.md`](../CLAUDE.md)). Ссылки в скобках — на разделы `TZ.md`/
`CONCEPT.md` с деталями реализации конкретного пункта.

Отмечать пункт `- [x]` в том же PR, который его закрывает.

## Этап 1. Реестр участников и мультитенантный каркас

- [x] **1.1 Модели и миграции БД.** SQLAlchemy 2.0 async модели `Project`,
      `ProjectTopicSetting`, `ProjectSettings`, `User`, `ProjectMembership`;
      Alembic init + первая миграция. (TZ §2.1–2.5)
- [x] **1.2 Каркас приложения.** Конфиг через `pydantic-settings`, асинхронная
      сессия БД, точка входа режима `bot+api` (aiogram + FastAPI на одном
      ASGI/uvicorn), `GET /health`. (TZ §3.1, §6.2)
- [x] **1.3 Создание проекта при добавлении бота.** Хендлер `my_chat_member` →
      создание `Project`/`ProjectSettings`/первого `User`+`ProjectMembership(admin)`.
      (TZ §3.3, шаг 2)
- [x] **1.4 `/setup_registration`.** Идемпотентный вызов внутри топика →
      сохранение `Project.default_thread_id`; создание `Project`, если ещё нет
      (общий путь с 1.3). (TZ §3.3, шаг 1; §3.5)
- [x] **1.5 Пост регистрации.** Публикация сообщения с inline URL-кнопкой
      `t.me/<bot>?start=<invite_payload>` в нужный топик и напоминания
      закрепить его вручную, сохранение `pinned_message_id`; закрепление и
      открепление (в т.ч. старого поста при переносе топика) — полностью на
      ответственности администратора чата, бот их не выполняет.
      (TZ §3.3, шаг 3; §4.1)
- [x] **1.6 `/start` и регистрация участника.** Парсинг `invite_payload`, upsert
      `User`/`ProjectMembership(member)`, приветственное сообщение;
      `/start` без payload — подсказка. (TZ §3.3, шаги 4–5; §4.1)
- [x] **1.7 `/all`.** Сбор упоминаний активных участников (`@username` или
      text-mention), разбивка на несколько сообщений при превышении лимита
      длины, троттлинг. (TZ §4.2; §6.1 rate limiting)
- [x] **1.8 Админ-команды реестра.** `/members`, удаление участника
      (`status=removed`, `removed_by`/`removed_at`), `/add_admin` — с проверкой
      `role=admin` на бэкенде. (TZ §4.1; §6.1 права ролей)
- [x] **1.9 `/set_topic`.** Привязка топика к категории (`events` /
      `money_collections` / `general`) через upsert `ProjectTopicSetting`,
      функция `resolve_thread_id(project_id, category)` для дальнейшего
      переиспользования. (TZ §3.5)
- [x] **1.10 Меню команд бота (`setMyCommands`).** Регистрация подсказок команд
      по `/` через `bot.set_my_commands()` при старте приложения, отдельно для
      `BotCommandScopeAllPrivateChats` (`/start`) и
      `BotCommandScopeAllGroupChats` (`/setup_registration`, `/set_topic`,
      `/all`, `/members`, `/remove_member`, `/add_admin`). (TZ §3.6)
- [x] **1.11 Топик регулирования прав (`rights`) и гейт admin-команд.** Категория
      `TopicCategory.RIGHTS` в `/set_topic`/`/unset_topic`; новая команда
      `/remove_admin` (понижение `role=admin` → `role=member`, только `role=owner`,
      инлайн-выбор → подтверждение, симметрично `/add_admin`); гейт по топику
      `rights` для `/members`, `/remove_member`, `/add_admin`, `/remove_admin` с
      fallback, если топик не назначен или чат без топиков. (TZ §2.2, §3.5, §3.7,
      §4.1)

## Этап 2. Мероприятия: создание и RSVP

- [x] **2.1 Каркас Web App.** Vite + React + TypeScript, `@telegram-apps/sdk`,
      `@telegram-apps/telegram-ui`, раздача статики; генерация TS-типов из
      OpenAPI (`openapi-typescript`). Заложить визуальный язык из
      [`WEBAPP_DESIGN.md`](./WEBAPP_DESIGN.md): семантические токены на
      `themeParams`, акцентный цвет — одним сменяемым токеном `--accent`
      (финальный цвет пока не выбран), без хардкода акцента в компонентах.
      (TZ §1.2 таблица «Web App фронтенд»)
- [x] **2.2 Кнопка открытия Web App.** Публичный базовый URL Mini App в конфиг
      (тот же origin, что вебхук за Tailscale Funnel; статика уже раздаётся под
      `/app`, см. `app._mount_webapp`); helper сборки `web_app`-URL с контекстом
      проекта и inline-кнопки (по аналогии с `services/registration_post.py`).
      Команда `/new_event` **только в личке** (`F.chat.type == "private"`, как
      `/start`) → сообщение с `InlineKeyboardButton(web_app=…)`; если пользователь
      состоит в нескольких проектах — сначала инлайн-выбор проекта. Регистрация в
      `PRIVATE_COMMANDS` / `setMyCommands`. Фронт: чтение `project` из URL,
      проброс в `apiFetch`, режимы «вне Telegram» и «без project-контекста». Сама
      форма и `POST /api/events` — задача 2.5. (TZ §3.2, §3.8, §4.3)
- [x] **2.3 Валидация `initData` на бэкенде.** Проверка `hash` (HMAC,
      `hmac.compare_digest`), `auth_date`, извлечение `tg_user_id`; FastAPI
      dependency, переиспользуемая всеми `/api/*`. (TZ §3.2)
- [x] **2.4 Модели `Event`, `EventCoOrganizer`, `EventRSVP` + миграция.**
      Включая `Event.ends_at`, `Event.attendance_finalized_at`,
      `EventRSVP.updated_by`. (TZ §2.6–2.8)
- [x] **2.5 Форма создания мероприятия + `POST /api/events`.** Поля из TZ §4.3
      п.2 (в т.ч. опциональный `ends_at`, со-организаторы — от нуля и больше,
      создатель может снять чекбокс и с себя), создание `Event`+
      `EventCoOrganizer`, публикация анонса в топик категории `events` с
      кнопками «Участвую»/«Не участвую», `announcement_message_id`.
      (TZ §3.5; §4.3)
- [x] **2.6 Обработка RSVP + живое обновление анонса.** Callback-хендлер
      upsert `EventRSVP` (`updated_by = user_id`), `editMessageText` анонса с
      пересчётом счётчика и списка никнеймов подтвердивших при каждом
      нажатии. (TZ §4.3 «RSVP»)
- [x] **2.7 Редактирование мероприятия.** Команда `/edit_event` в личке → бот
      присылает список мероприятий, где у вызвавшего есть право (`EventCoOrganizer`,
      либо, если таких строк нет, `created_by`/`role=admin`), с `web_app`-кнопкой
      у каждого; Web App-форма с предзаполнением, повторная проверка прав при
      сохранении, `editMessageText` анонса, личные уведомления подтвердившим. Без
      кнопки «Редактировать» под анонсом в группе (TZ §3.8, §4.3).
      (TZ §4.3 «Редактирование/отмена»)
- [ ] **2.8 Отмена мероприятия.** Действие в форме редактирования или команда
      `/cancel_event` в личке → `status=cancelled`, пометка анонса, уведомление
      подтвердивших. (TZ §4.3 «Редактирование/отмена»)
- [ ] **2.9 Домашний экран Web App + постоянная кнопка-меню.** Глобальная
      `setChatMenuButton` (без `chat_id`) → `MenuButtonWebApp` на фиксированный URL
      хаба, вызывается при старте рядом с `set_bot_commands` (`bot/commands.py`).
      Эндпоинт списка активных `ProjectMembership` текущего пользователя (через ту же
      `initData`-dependency, что и остальные `/api/*`). Фронт: домашний экран-хаб —
      кто пользователь, в каком проекте, кнопки-переходы на действия (создать
      мероприятие и т.п.); состояния «0 проектов» (не зарегистрирован → deep-link),
      «1 проект» (сразу хаб), «несколько» (выбор проекта). Только навигация, **без**
      статистики посещаемости (полноценный «Личный кабинет» — backlog, TZ §5). Не
      блокирует и не блокируется 2.5–2.8, но хабу нужны реальные экраны-цели, так
      что осмысленно делать после 2.5. (TZ §3.6, §3.8)

## Технический долг

- [x] **Миграция Web App SDK на `@tma.js/*`.** `@telegram-apps/sdk@3.11.8` был
      заморожен (последняя публикация 2025-12-05), его транзитивные
      `@telegram-apps/bridge` / `transformers` / `types` помечены deprecated
      («Use @tma.js/… instead») и точечно пинили уязвимый `valibot`
      (`GHSA-vqpr-j7v3-hqw9` ReDoS, `GHSA-5qjj-4xww-7phc`) без шанса на
      апстрим-фикс. Заменено на `@tma.js/sdk@3.3.0` (тот же мажор, `valibot@1.4.2`
      → `npm audit` 0 уязвимостей). API v3.3 отличается от `@telegram-apps/sdk`:
      `themeParams.mountSync()` → `themeParams.mount()`, ключи `themeParams` —
      через сигнал-геттеры инстанса (`themeParams.secondaryBgColor()` и т.п.).
      Поверхность — 3 файла (`webapp/src/api/client.ts`, `telegram/init.ts`,
      `theme/applyThemeParams.ts`). `@telegram-apps/telegram-ui` остаётся
      (преемника нет, не deprecated; именно он пинит React на 18). Детали —
      `webapp/README.md` «Известные ограничения».

- [x] **Ревью админ-команд реестра скиллом `/grill-me`.** Пройтись по
      `/members`, `/remove_member`, `/add_admin` и логике ролей
      (`owner`/`admin`/`member`, см. 1.8) — реализация шла быстрой итерацией,
      и уже по ходу работы нашлись два бага (реактивация удалённого участника
      при повторном `/start`, отсутствие защиты владельца от удаления и от
      неконтролируемого назначения новых админов). Сигнал стресс-тестировать
      эту область целенаправленно, а не полагаться только на обычное ревью.
      Результат ревью — топик `rights` и гейт admin-команд (1.11), новые
      команды `/unset_topic`/`/remove_admin`, зафиксированный пробел
      `/transfer_owner` (TZ §5).

- [x] **`/set_topic`: порядок проверок вводит не-админа в заблуждение.**
      В `src/meetup_bot/bot/handlers/set_topic.py` валидация категории стояла
      раньше проверки роли. Если не-админ вызывал `/set_topic` без категории
      (или с некорректной), бот отвечал «Укажите категорию после команды…»,
      хотя настоящая причина отказа — отсутствие прав. Указав корректную
      категорию, тот же пользователь получал уже «Эту команду может вызвать
      только администратор проекта». Починка: проверка существования проекта
      и `role=admin` перенесена раньше разбора аргументов (тот же порядок — в
      новой команде `/unset_topic`). Закрыто в PR 1.11. (TZ §3.5)

- [ ] **Полировка UI формы создания мероприятия (задача 2.5).** По итогам ручной
      проверки первой версии формы (`webapp/src/event-form/`):
      - вся вёрстка выглядит слишком мелкой — пересмотреть масштаб (базовый
        размер шрифта, отступы карточек/полей, тач-цели) под телефон;
      - `<input type="datetime-local">` на десктопе показывает только выбор даты,
        без времени; на телефоне при тёмном акцентном токене текст виджета
        слишком тёмный / низкий контраст. Нужен свой контрол выбора даты и
        времени (`PickerRow` из `WEBAPP_DESIGN.md`) вместо нативного `datetime-local`,
        либо явное решение по стилизации нативного виджета под токены темы.
      Правки косметические, на контракт `POST /api/events` не влияют. Может
      делаться вместе с задачей 2.7 (та же форма, предзаполненная) или отдельно.
