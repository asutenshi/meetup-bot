# Техническое задание: телеграм-бот для системных встреч дружеской компании

> Документ операционализирует решения, зафиксированные в `CONCEPT.md` (единственный
> источник правды по фичам). Новых фич сверх `CONCEPT.md` здесь не вводится — только
> техническая реализация принятого скоупа.

---

## 1. Технологический стек

### 1.1 Критерии выбора

Проект — хобби-инициатива для одной (в перспективе нескольких) дружеских компаний,
без коммерческих целей на старте. Ключевые критерии:

- поддержку тянут 1–2 разработчика в свободное время — приоритет простоте над
  «промышленной» масштабируемостью;
- инфраструктура должна стоить копейки (речь о десятках, не сотнях пользователей на
  проект, и о единицах-десятках проектов в обозримом будущем);
- язык серверной части — тот, на котором разработчик свободно и быстро пишет
  (**Python**), чтобы не тратить время маленькой команды на контекст-свитчинг между
  незнакомой и знакомой экосистемой. Полностью одноязычным стек всё равно не
  получится: Telegram Mini App — браузерная технология, фронтенд Web App неизбежно
  на TypeScript/React. Поэтому цель — не «один язык везде», а «Python везде, где он
  уместен» (бот, бэкенд, воркер, скрипты), TypeScript — только там, где без него
  нельзя (клиентский код Web App);
- мультитенантность нужна на уровне модели данных, но не требует сложной оркестрации
  (нет отдельных бот-инстансов на проект, нет биллинга).

### 1.2 Итоговый выбор

| Слой | Выбор | Почему |
|---|---|---|
| Язык (бэкенд + бот) | **Python 3.12+** | Основной язык разработчика — быстрее писать и проще поддерживать, чем осваивать параллельно вторую серверную экосистему ради «единого языка на бумаге». Зрелая асинхронная экосистема (asyncio) полностью закрывает потребности бота с вебхуками и HTTP API. Общие типы с фронтендом теряются (см. ниже), но это разумная цена за скорость разработки бэкенд-части. |
| Тг-бот фреймворк | **aiogram 3.x** | Async-first, активно поддерживается, встроенная поддержка `web_app`-кнопок и `WebAppData`, FSM для диалоговых сценариев, хорошая документация и большое русскоязычное комьюнити (актуально для поддержки в перспективе). python-telegram-bot — жизнеспособная альтернатива (тоже async с v20), но API aiogram чуть более «pythonic» и легче интегрируется в ASGI-приложение вместе с FastAPI на одном event loop. |
| Бэкенд | **Монолит**: бот и backend API — один Python-процесс (**FastAPI** как ASGI HTTP-слой поверх того же кода, что и бот, оба на asyncio) | При таком масштабе (друзья, десятки пользователей) разделение бот-сервиса и backend API в отдельные развёртываемые сервисы — чистые накладные расходы на деплой/мониторинг без выигрыша. Один процесс = один деплой, один лог, один health-check. FastAPI даёт валидацию через Pydantic и автогенерацию OpenAPI-схемы «из коробки» — она же используется для генерации TS-типов фронтенду (см. ниже). Код внутри всё равно разложен на модули (`bot/`, `api/`, `db/`, `scheduler/`), так что разделение на сервисы в будущем — рефакторинг, а не переписывание. |
| СУБД | **PostgreSQL** | Нужны нормальные транзакции и внешние ключи для мультитенантной модели (Project → Event → RSVP/Attendance и т.д.), и это стандарт, который «просто работает» с любым дешёвым хостингом. SQLite рассматривался ради минимизации инфраструктуры, но при вероятном будущем сборе денег (backlog) и параллельных cron-задачах предпочтительнее полноценная БД с конкурентным доступом. |
| ORM | **SQLAlchemy 2.0 (async) + Alembic** для миграций | Индустриальный стандарт в Python-экосистеме, предсказуемое поведение на сложных запросах и транзакциях мультитенантной модели, Alembic — зрелый инструмент миграций. SQLModel (от автора FastAPI, Pydantic поверх SQLAlchemy) — жизнеспособная альтернатива с чуть меньшим боилерплейтом, но менее зрелая на сложных миграциях/связях, поэтому не выбрана как основной вариант. Визуального аналога Prisma Studio в экосистеме нет — для ручной модерации реестра на первых порах достаточно language-agnostic Adminer/pgweb третьим контейнером в Docker Compose (или прямых `psql`-запросов). |
| Web App фронтенд | **React + TypeScript + Vite**, UI — **@telegram-apps/telegram-ui** (компоненты в нативной телеграмной стилистике), интеграция с Telegram — **@tma.js/sdk** | Telegram Mini App — браузерная технология, здесь Python неуместен: React остаётся самым низким порогом входа и самой большой базой примеров именно для Telegram Mini Apps, готовый UI-кит под тему Telegram экономит время на вёрстку для одного человека. Общие типы с бэкендом (модели, DTO), которые в чистом TS-стеке давал shared-пакет, здесь получаются генерацией TS-типов из OpenAPI-схемы FastAPI (например, `openapi-typescript`) — отдельный шаг сборки, но без ручного дублирования интерфейсов. Визуальный язык (направление оформления, компоненты, токены, требование к сменяемому одним токеном акцентному цвету) вынесен в [`WEBAPP_DESIGN.md`](./WEBAPP_DESIGN.md). |
| Планировщик напоминаний | **APScheduler внутри отдельного Python-процесса** (worker с тем же кодом и БД-моделями, отдельная точка входа) | При таком масштабе очередь задач (Celery + Redis) — избыточная инфраструктура. Периодический опрос БД (например, раз в 15 минут) через APScheduler полностью покрывает потребность в напоминаниях с точностью до часа, которая тут и не нужна. Celery+Redis (или Celery beat) — кандидат на замену, если/когда возрастёт нагрузка или потребуется точная доставка «ровно в срок». |
| Хостинг | **Домашний сервер на Proxmox (VM/LXC) + Docker Compose + Tailscale Funnel** | Оборудование уже есть, белого IP нет — Tailscale Funnel даёт публичный HTTPS-домен с валидным сертификатом без проброса портов и без белого IP (нужен и для вебхука бота, и для Web App — см. раздел 3.1). Tailscale уже используется для доступа к самому серверу, поэтому не добавляет нового стороннего провайдера в инфраструктуру. Фактическая стоимость — только электричество. См. сравнение и риски ниже. |
| Менеджер пакетов (Python) | **uv** | Единый инструмент для резолва/установки зависимостей, виртуального окружения и запуска (`uv run`), заметно быстрее pip/poetry за счёт кэша и параллельной установки. Зависимости и их версии фиксируются в `pyproject.toml` + `uv.lock` (лок-файл коммитится в репозиторий для воспроизводимых сборок). В Docker-образе `app`-сервиса (раздел 3.1) используется как на этапе сборки (`uv sync --frozen`), так и для запуска (`uv run`) — не требует отдельной установки Python-зависимостей вне `uv`. |

### 1.3 Хостинг: сравнение вариантов

**Отправная точка: нет белого IP.** Домашний сервер за NAT провайдера не может напрямую
принимать входящие HTTPS-соединения — ни вебхук бота, ни, что важнее, обращения
Telegram-клиента к Web App (Telegram требует для `web_app`-кнопок публичный `https://`
с настоящим сертификатом — самоподписанный или недоступный извне адрес клиент
откроет). Проброс портов на роутере — не вариант без белого IP от провайдера. Решение —
исходящий туннель, который делает связность независимой от того, кто инициирует
соединение.

**Вариант А — домашний сервер на Proxmox + Tailscale Funnel (рекомендуется).**
На Proxmox поднимается один Linux-хост (VM или LXC-контейнер), на нём — Docker Compose с
теми же контейнерами, что и на VPS: `app` (бот + API + worker-профиль того же образа),
`postgres`. Tailscale уже установлен на хосте для администрирования сервера через
tailnet, поэтому для публичного входа используется тот же клиент — команда
`tailscale funnel <порт>` (в фоне — `--bg`) пробрасывает локальный порт `app`-сервиса
наружу через edge-узлы Tailscale (работает из-за NAT так же, как long polling, без
проброса портов на роутере) и выдаёт публичный домен вида `<host>.<tailnet>.ts.net` с
автоматическим валидным TLS-сертификатом. Отдельного конфиг-файла ingress-правил не
требуется — маршрут «домен → локальный порт» задаётся самой командой `tailscale serve`/
`funnel`. TLS терминируется на стороне Tailscale, поэтому отдельный Caddy/Nginx для
сертификатов внутри сети не обязателен — роль реверс-прокси (раздел 3.1, компонент 4) в
этом варианте берёт на себя Tailscale Funnel; Caddy/Nginx локально можно оставить только
для внутренней маршрутизации между несколькими контейнерами, если весь трафик заведён на
один публичный порт.

Плюсы: оборудование уже есть, фактическая стоимость — только электричество; полный
контроль над железом; не добавляет нового стороннего провайдера — Tailscale уже
используется для доступа к серверу; бесплатный тариф без ограничений, существенных для
этого масштаба.
Минусы и как их закрыть:
- **зависимость от домашнего интернета и электричества.** Если дома пропадёт свет или
  провайдер — бот и Web App недоступны, пока не восстановится связь. Для хобби-проекта
  друзей (не 24/7-критичного сервиса) это приемлемый риск, но стоит явно предупредить
  участников, что бот — не банковское приложение. Снижает риск: health-check
  (раздел 6.2) на внешнем аптайм-мониторе, который просто покажет, когда сервис лежит,
  а не попытается его поднять — самостоятельно среагировать на пропажу дома всё равно
  некому кроме разработчика;
- **бэкапы обязаны быть внешними** (раздел 6.3) даже в большей степени, чем на VPS —
  при отказе домашнего диска/материнки восстанавливаться неоткуда, кроме внешнего
  хранилища; локальной копии на том же физическом железе недостаточно;
- **демон `tailscaled` — дополнительная точка отказа**, за обновлением которого тоже
  нужно следить (хотя обновляется редко и работает стабильно на практике);
- Proxmox добавляет слой виртуализации поверх домашнего железа — с одной стороны,
  удобные снапшоты VM/LXC перед рискованными изменениями, с другой — ещё один компонент,
  за которым нужно следить (обновления Proxmox, ресурсы хоста).

**Вариант Б — один VPS + Docker Compose (fallback, если домашний хостинг окажется
неудобным).**
Тот же набор контейнеров, но без Tailscale Funnel: белый IP есть у самого VPS, поэтому
Caddy/Nginx на нём терминирует TLS через Let's Encrypt напрямую (например Hetzner CX22
~4-5 €/мес). Плюсы: не зависит от домашнего интернета/электричества, предсказуемая
доступность, никакого vendor lock-in на Tailscale. Минусы: небольшая ежемесячная
стоимость вместо «почти бесплатно», плюс разработчик всё равно сам отвечает за
обновление ОС/докера на арендованной машине. Имеет смысл держать в уме как путь
эволюции, если домашний сервер начнёт причинять больше неудобств, чем экономит.

**Вариант В — serverless (AWS Lambda/Google Cloud Functions + Neon/Supabase + внешний
cron).**
Плюсы: не нужно администрировать сервер вообще, автоскейлинг. Минусы для этого проекта:
- long-running процесс планировщика напоминаний плохо ложится на serverless-модель —
  потребуется отдельный сервис для cron (EventBridge Scheduler / Cloud Scheduler) и
  это уже третья платформа в связке;
- холодные старты у бесплатных тарифов заметны в вебхуке бота (задержка ответа на
  нажатие кнопки, ощущается как «тормозит»);
- три разных провайдера (хостинг кода, БД, cron) вместо одного — больше мест, где что-то
  может разъехаться по конфигурации, что для команды из 1-2 человек — не выигрыш в
  простоте, а его иллюзия.

**Вариант Г — PaaS с постоянным процессом (Fly.io / Railway).**
Не нужно администрировать ОС, процесс не «засыпает», как в классическом serverless,
поэтому cron-воркер работает нормально. Хорошая альтернатива варианту Б, если совсем не
хочется трогать `apt update` руками. Стоимость сопоставима или чуть выше VPS.

**Итог:** вариант А — основная рекомендация, раз оборудование уже есть, а Tailscale
Funnel полностью снимает проблему отсутствия белого IP и для вебхука, и для Web App
одним и тем же механизмом; вариант Б — понятный путь отступления, если домашний аптайм
станет проблемой; варианты В/Г — не рассматриваются как приоритетные при текущем
масштабе и уже выбранном железе.

## 2. Модель данных

Ниже — сущности как таблицы (поля и связи). Правила: все таблицы, кроме `User`,
скоуплены на `project_id` (мультитенантность и изоляция данных). `User` — глобальная
сущность, т.к. один Telegram-аккаунт может состоять в нескольких проектах.

Поля, помеченные ниже как `enum`, реализуются как `VARCHAR` + `CHECK`-констрейнт
(`sa.Enum(PyEnum, native_enum=False)` в SQLAlchemy), а не нативный тип `ENUM` Postgres.
Нативный тип даёт то же самое ограничение на уровне БД, но крайне неудобен при
изменении набора значений (нельзя удалить/переименовать значение без пересоздания
типа и всех ссылающихся столбцов) — а такие поля, как `Event.status` или роли,
вероятно будут дополняться по мере роста фич. `VARCHAR` + `CHECK` меняется обычной
Alembic-миграцией, при этом типизация на стороне Python-кода обеспечивается классом
`enum.Enum`.

### 2.1 `Project`
- `id` (PK, uuid/serial)
- `tg_chat_id` (bigint, unique) — id группового чата компании в Telegram
- `name` (string) — человекочитаемое название проекта
- `invite_payload` (string, unique) — значение `project_id` для deep-link
  (`t.me/bot?start=<invite_payload>`); может совпадать с `id`, но вынесено отдельным
  полем на случай ротации ссылки
- `pinned_message_id` (bigint, nullable) — id последнего опубликованного поста
  регистрации с кнопкой (закрепляет его вручную администратор чата, бот не
  закрепляет автоматически — см. 3.3, шаг 3)
- `default_thread_id` (bigint, nullable) — id топика (forum thread) группового чата,
  куда бот шлёт сообщения по умолчанию: устанавливается автоматически при вызове
  `/setup_registration` внутри нужного топика (см. 3.3, 3.5) и туда же публикуется
  пост регистрации. `null`, если чат не форум (топиков нет) — тогда бот
  просто шлёт в чат без указания топика. Используется как fallback, когда для
  конкретной категории сообщений (мероприятия, сборы и т.п.) не задан отдельный топик
  в `ProjectTopicSetting`
- `is_active` (bool, default true)
- `created_at` (timestamp)

### 2.2 `ProjectTopicSetting`
- `id` (PK)
- `project_id` (FK → Project)
- `category` (enum: `events`, `money_collections`, `general`, `rights` — расширяемо под
  будущие категории сообщений; `general` используется как явная категория для `/all` и
  прочих сообщений, не относящихся к более специфичной категории; `rights` — особая
  категория, не про маршрутизацию исходящих сообщений, а про то, откуда разрешено
  вызывать команды регулирования прав, см. 3.7)
- `thread_id` (bigint) — id топика, куда слать сообщения этой категории
- `updated_at` (timestamp)
- Уникальность: (`project_id`, `category`). Наличие строки для категории переопределяет
  `Project.default_thread_id` для сообщений этой категории (см. 3.5); отсутствие строки
  означает «слать в топик по умолчанию».

### 2.3 `ProjectSettings` (1:1 к `Project`)
- `project_id` (PK, FK → Project)
- `reminder_days_threshold` (int, default 14) — через сколько дней «не виделись»
  слать личное напоминание участнику
- `missed_events_escalation_count` (int, default 3) — после скольких пропущенных
  подряд мероприятий переключаться с личных напоминаний участнику на уведомление
  организатора/админа
- `all_command_throttle_seconds` (int, default 180) — минимальный интервал между
  повторными вызовами `/all` в проекте (раздел 4.2; 6.1 rate limiting), настраивается
  админом
- `timezone` (string, default `Europe/Moscow`) — для корректного расчёта времени
  напоминаний
- `reminder_send_hour` (int, default 20) — час локального времени проекта
  (`timezone`), в который worker рассылает личные напоминания и эскалации
  (раздел 3.4, п.2–3), чтобы уведомления не приходили ночью. Финализации явки
  (п.1) не касается — она привязана к полуночи следующего дня намеренно
- `updated_at` (timestamp)

`reminder_days_threshold`, `missed_events_escalation_count`, `reminder_send_hour`
и `timezone` меняет админ командой `/settings` в групповом чате (задача 4.5):
без аргументов — список текущих значений, `/settings <параметр> <значение>` —
установка нового с валидацией (диапазоны для чисел, разбор имени зоны IANA для
`timezone`). `all_command_throttle_seconds` пока правится только напрямую в БД.

### 2.4 `User`
- `id` (PK)
- `tg_user_id` (bigint, unique) — Telegram user id
- `username` (string, nullable)
- `first_name` (string)
- `last_name` (string, nullable)
- `created_at` (timestamp)
- `last_seen_at` (timestamp) — последнее взаимодействие с ботом/Web App (для диагностики)

### 2.5 `ProjectMembership`
- `id` (PK)
- `project_id` (FK → Project)
- `user_id` (FK → User)
- `role` (enum: `admin`, `member`)
- `status` (enum: `active`, `removed`)
- `registered_at` (timestamp)
- `removed_at` (timestamp, nullable)
- `removed_by` (FK → User, nullable)
- `last_attended_at` (timestamp, nullable) — денормализованное поле, обновляется
  автоматически при финализации мероприятия по списку `EventRSVP` (см. §3.4), либо
  точечно при постфактум-правке `EventRSVP` после финализации; используется
  планировщиком напоминаний без пересчёта по всей истории
- `consecutive_missed_events` (int, default 0) — денормализованный счётчик подряд
  пропущенных мероприятий, обновляется по той же схеме, что и `last_attended_at`
- `last_reminder_sent_at` (timestamp, nullable) — когда участнику последний раз
  ушло личное напоминание «давно не виделись» (§3.4, п.2); троттлинг — не чаще
  одного раза в сутки
- `last_escalation_sent_at` (timestamp, nullable) — когда по этому участнику
  последний раз ушла эскалация организатору/админу (§3.4, п.3); троттлинг — не
  чаще одного раза в неделю
- Уникальность: (`project_id`, `user_id`)

### 2.6 `Event`
- `id` (PK)
- `project_id` (FK → Project)
- `title` (string, nullable — если поле не заводили отдельно от описания)
- `description` (text)
- `date` / `starts_at` (timestamp) — дата и время начала
- `ends_at` (timestamp, nullable) — дата и время окончания, для мероприятий на
  несколько дней; `null` — однодневное мероприятие, эффективным окончанием считается
  `starts_at`. Используется только для расчёта момента финализации явки (см. §3.4),
  не влияет на RSVP/анонс
- `location` (string)
- `budget_per_person` (decimal, nullable)
- `seats_limit` (int, nullable) — «мягкий» ориентир: сколько человек нужно собрать,
  чтобы мероприятие состоялось, а не жёсткий потолок. RSVP по достижении лимита не
  блокируется, число подтвердивших может его превысить — счётчик в анонсе тогда
  условный, вида «17/15» с пометкой (см. §4.3 «RSVP»)
- `status` (enum: `planned`, `cancelled`, `completed`)
- `created_by` (FK → User)
- `announcement_message_id` (bigint, nullable) — id сообщения-анонса в группе (для
  редактирования/пометки «отменено» и для живого обновления счётчика/списка
  подтвердивших, см. §4.3)
- `attendance_finalized_at` (timestamp, nullable) — момент, когда воркер зафиксировал
  список `EventRSVP` как факт явки и обновил `ProjectMembership.last_attended_at` /
  `consecutive_missed_events` (см. §3.4, п.1); пока `null` — мероприятие ещё не
  прошло финализацию, RSVP можно свободно поправлять
- `created_at`, `updated_at` (timestamp)

### 2.7 `EventCoOrganizer`
- `id` (PK)
- `event_id` (FK → Event)
- `user_id` (FK → User)
- `added_at` (timestamp)
- Уникальность: (`event_id`, `user_id`). Таблица может быть пустой — мероприятие без
  организатора (CONCEPT.md, раздел 3). По умолчанию при создании в неё первой строкой
  попадает создатель мероприятия, но он может снять чекбокс и с себя (раздел 4.3) —
  тогда для этого `event_id` строк нет вовсе. Право редактировать/отменять мероприятие
  и постфактум корректировать чужой `EventRSVP` в этом случае проверяется не по этой
  таблице, а по `Event.created_by` либо по `role=admin` в `ProjectMembership`.

### 2.8 `EventRSVP` (намерение и факт)
- `id` (PK)
- `event_id` (FK → Event)
- `user_id` (FK → User)
- `status` (enum: `going`, `not_going`)
- `responded_at` (timestamp)
- `updated_by` (FK → User, nullable) — кто последним менял статус: сам участник
  (тогда равен `user_id`) либо организатор/создатель/админ, постфактум
  скорректировавший чужой RSVP (см. §3.4, п.1)
- `updated_at` (timestamp)
- Отсутствие строки для (`event_id`, `user_id`) = участник ещё не ответил на RSVP
  («не прочитал / думает»); в анонсе эта группа отдельно не показывается (§4.3
  «RSVP»), но при финализации явки (§3.4) она учитывается как «не присутствовал».
- Уникальность: (`event_id`, `user_id`). Отдельной таблицы «факта явки» нет —
  финальное значение `status` на момент финализации мероприятия (`Event.
  attendance_finalized_at`, см. §3.4) и есть факт посещения; отдельная
  постфактум-отметка явки в модели не предусмотрена (см. CONCEPT.md, раздел 3).

### 2.9 `MoneyCollection` (backlog, но заложено в модель)
- `id` (PK)
- `project_id` (FK → Project)
- `event_id` (FK → Event, nullable) — привязка к мероприятию, если сбор создан «от него»
- `title` (string)
- `total_amount` (decimal, nullable) — если считается «поровну от общей суммы»
- `default_share_amount` (decimal, nullable) — если задаётся сразу сумма с человека
- `created_by` (FK → User)
- `payment_profile_id` (FK → PaymentProfile) — какие реквизиты показывать
- `notify_channel` (enum: `dm`, `group`) — куда шлётся уведомление, выбирает создатель
- `status` (enum: `active`, `cancelled`, `completed`)
- `created_at`, `updated_at` (timestamp)

### 2.10 `MoneyCollectionParticipant` (backlog)
- `id` (PK)
- `collection_id` (FK → MoneyCollection)
- `user_id` (FK → User)
- `amount_due` (decimal) — по умолчанию равная доля, редактируется вручную
- Уникальность: (`collection_id`, `user_id`)

### 2.11 `PaymentProfile` (backlog) — реквизиты пользователя
- `id` (PK)
- `user_id` (FK → User)
- `label` (string, nullable — например «Тинькофф», «Сбер»)
- `bank_name` (string)
- `account_number` (string)

- Уникальность: (`collection_id`, `user_id`)

## 3. Архитектура

### 3.1 Компоненты

1. **App-сервис** (Python, один Docker-образ, два режима запуска):
   - режим `bot+api` — принимает вебхуки Telegram (aiogram, смонтированный как ASGI-роут)
     и HTTP-запросы Web App (FastAPI), слушает на одном порту через uvicorn, за
     реверс-прокси;
   - режим `worker` — тот же код, entrypoint для планировщика напоминаний (APScheduler),
     без приёма входящих HTTP-запросов. Запускается вторым контейнером из того же
     образа в `docker-compose.yml`, чтобы падение долгого cron-цикла не роняло приём
     сообщений бота, и наоборот.
2. **PostgreSQL** — единственное хранилище состояния.
3. **Web App фронтенд** — статическая SPA (React), собирается Vite, раздаётся с
   отдельного под-пути или под-домена, обращается к App-сервису по HTTPS.
4. **Публичный HTTPS-вход и маршрутизация** — терминирует TLS, маршрутизирует
   `/api/*` → App-сервис, `/` (или отдельный домен `app.example.com`) → статика Web App,
   принимает вебхук Telegram на отдельном пути. Конкретная реализация зависит от
   варианта хостинга (раздел 1.3): на домашнем сервере эту роль берёт на себя
   Tailscale Funnel (`tailscale funnel`, TLS терминируется на стороне Tailscale); на
   VPS — классический Caddy/Nginx с TLS через Let's Encrypt.

### 3.2 Аутентификация Web App через Telegram `initData`

1. При открытии Web App Telegram кладёт в `window.Telegram.WebApp.initData` подписанную
   строку с данными пользователя (`user`, `auth_date`, `hash` и т.д.) и, если Web App
   открыт по `startapp`-параметру, полезной нагрузкой из ссылки.
2. Frontend при каждом запросе к API кладёт эту строку целиком в заголовок
   (`X-Telegram-Init-Data`).
3. Backend валидирует на каждый запрос:
   - парсит query-string, вынимает `hash`, остальные пары сортирует по ключу и
     собирает `data_check_string`;
   - считает `secret_key = HMAC_SHA256(bot_token, "WebAppData")`;
   - считает `HMAC_SHA256(data_check_string, secret_key)` и сравнивает с `hash`
     (константное сравнение через `hmac.compare_digest`, не через `==`);
   - проверяет `auth_date` — не старше, например, 24 часов (защита от replay);
   - если подпись валидна — достаёт `tg_user_id` из поля `user`.
4. Далее backend по `tg_user_id` + `project_id` (передаётся отдельным параметром запроса;
   формы Web App открываются в контексте конкретного проекта) ищет
   `ProjectMembership`. Если записи нет — API отвечает `403 not_registered`, и Web App
   показывает предупреждение: «Бот не может писать вам в личку, пока вы не
   зарегистрированы» + кнопка-ссылка на deep-link регистрации.
   Исключение — домашний экран-хаб (раздел 3.8): он открывается глобальной
   кнопкой-меню без `project_id` и сам получает список активных `ProjectMembership`
   пользователя отдельным эндпоинтом (только по `initData`), чтобы затем открыть
   нужную форму уже с `project_id`. Это отдельно от валидности
   `initData` — технически Telegram *может* опознать пользователя даже без регистрации,
   но право писать в ЛС даёт только состоявшийся `/start` в приватном чате с ботом.

### 3.3 Deep-link флоу регистрации (технически)

1. Админ, добавивший бота в группу, вызывает команду `/setup_registration` **внутри
   того топика**, который должен стать топиком бота по умолчанию (если в чате нет
   топиков — просто в общем чате). Команду можно вызвать повторно в другом топике,
   чтобы позже поменять топик по умолчанию (см. 3.5) — идемпотентно, не плодит новых
   `Project`.
2. При событии `my_chat_member` (бот добавлен в группу, статус `member`/`administrator`)
   либо при первом вызове `/setup_registration` backend:
   - создаёт `Project` (если для этого `tg_chat_id` его ещё нет), `ProjectSettings`
     со значениями по умолчанию;
   - сохраняет `message_thread_id` апдейта, которым была вызвана команда, в
     `Project.default_thread_id` (`null`, если апдейт не из топика);
   - создаёт `User` (если нет) и `ProjectMembership(role=admin)` для того, кто выполнил
     действие (поле `from` в апдейте).
3. Бот публикует в группу, в топик `default_thread_id` (см. 3.5), сообщение с
   inline-кнопкой-ссылкой `https://t.me/<bot_username>?start=<invite_payload>` и
   отдельным сообщением-напоминанием закрепить пост вручную; `pinned_message_id`
   (id поста с кнопкой) сохраняется в `Project`. Закрепление и открепление — на
   ответственности администратора чата: бот сам ничего не закрепляет и не
   открепляет (в том числе старый пост при повторной публикации в другом
   топике, см. шаг 1) — у бота не всегда есть на это права, а само закрепление
   — чувствительное действие.
4. Любой участник группы жмёт кнопку → Telegram открывает приватный чат с ботом и
   отправляет `/start <invite_payload>`.
5. Bot-хендлер `/start`:
   - парсит `invite_payload`, ищет `Project`;
   - upsert `User` по `tg_user_id` (данные берутся из апдейта: username, first/last name);
   - upsert `ProjectMembership(role=member, status=active)` (idempotent — повторный
     заход по той же ссылке не плодит дубликаты);
   - отвечает приветственным сообщением и кратко объясняет, что теперь будут личные
     напоминания.

### 3.4 Напоминания и эскалация (планировщик)

Worker-процесс раз в заданный интервал (рекомендация: каждые 15–30 минут — точность
до минуты тут не нужна) выполняет три независимых прохода по БД:

1. **Финализация явки по списку RSVP.**
   `Event.status = planned AND attendance_finalized_at IS NULL AND now() >= midnight(tz(project), (ends_at ?? starts_at).date + 1 day)`
   → для каждого такого мероприятия факт явки берётся прямо из текущего состояния
   `EventRSVP`: все строки со `status = going` — присутствовали, остальные активные
   участники проекта (включая тех, кто вообще не ответил на RSVP) — не присутствовали.
   Для присутствовавших — `ProjectMembership.last_attended_at = now()` (момент
   финализации) и `consecutive_missed_events = 0`; для отсутствовавших —
   `consecutive_missed_events += 1`. По завершении — `Event.attendance_finalized_at =
   now()`, повторно мероприятие джобой не обрабатывается. Момент финализации не
   привязан к точному времени окончания мероприятия специально — полночь следующего
   дня (в таймзоне проекта, `ProjectSettings.timezone`) даёт организатору (или
   создателю/админу, если организатора нет) запас времени, чтобы до этого момента
   поправить чьи-то ошибочные самоотметки через корректировку `EventRSVP` (см. §4.3).
   Правка `EventRSVP` **после** того, как `attendance_finalized_at` уже проставлен,
   пересчитывает `last_attended_at`/`consecutive_missed_events` точечно только для
   скорректированного участника, не трогая остальных и не откатывая
   `attendance_finalized_at`.
2. **Личное напоминание участнику «давно не виделись».**
   Для каждой активной `ProjectMembership` с `consecutive_missed_events < missed_events_escalation_count`
   и `now() - last_attended_at > ProjectSettings.reminder_days_threshold` (или
   `last_attended_at IS NULL` и от регистрации прошло больше порога) — личное сообщение
   с текстом «ты уже N дней не виделся…» и, если есть, ближайшим запланированным
   мероприятием. Троттлинг — не чаще одного такого напоминания в день на человека
   (например, поле `last_reminder_sent_at`).
3. **Эскалация организатору/админу.**
   Для `ProjectMembership.consecutive_missed_events >= missed_events_escalation_count` —
   вместо шага 2 персональные напоминания участнику прекращаются, вместо этого
   уведомляются со-организаторы ближайшего запланированного мероприятия (или админы
   проекта, если такого мероприятия нет либо у него нет со-организаторов) с текстом
   вида «X пропустил подряд N встреч, возможно стоит написать лично»; со-организаторы
   уже прошедших мероприятий получателями не становятся. Троттлинг аналогично —
   не чаще одного раза в какой-то период (например, раз в неделю на пару
   участник-проект), чтобы не заваливать организатора повторами.

Шаги 2 и 3 (в отличие от шага 1) отправляют людям сообщения, поэтому рассылают
их только в проходе, попавшем на час `ProjectSettings.reminder_send_hour` по
таймзоне проекта (по умолчанию 20:00) — чтобы уведомления не приходили ночью.
Проходы в остальные часы для шагов 2–3 — no-op (проверка порогов и рассылка
пропускаются). Час — меняемая величина (см. `ProjectSettings.reminder_send_hour`,
раздел 2.3).

`consecutive_missed_events` и `last_attended_at` обновляются в двух местах:
автоматически при финализации мероприятия (шаг 1 выше, по расписанию воркера) и
точечно при постфактум-правке `EventRSVP` организатором/создателем/админом после
финализации (шаг 1, последний абзац).

### 3.5 Топики группового чата

Групповой чат компании обычно ведётся с топиками (форум-режим), а бот — дополнение к
нему (см. `CONCEPT.md`, раздел 1), поэтому важно, чтобы разные виды сообщений бота не
расползались произвольно по топикам, а шли туда, куда сознательно указал админ.

**Категории сообщений.** Каждое проактивное (не являющееся прямым ответом на команду
в чате) групповое сообщение бота относится к одной из категорий
(`ProjectTopicSetting.category`, раздел 2.2):
- `events` — анонсы мероприятий, редактирование/отмена (раздел 4.3);
- `money_collections` — уведомления о сборах денег (backlog, раздел 5);
- `general` — всё остальное (кроме `/all`, см. ниже), в том числе пост регистрации,
  если для него нет более специфичной причины выделять отдельный топик.

Категория `rights` в этот список не входит — она не про маршрутизацию исходящих
сообщений, а про то, откуда разрешено вызывать admin-команды регулирования прав.
Привязывается тем же `/set_topic`, но описана отдельно в разделе 3.7, чтобы не
путать с логикой `resolve_thread_id` ниже.

**Разрешение топика при отправке.** Backend перед отправкой любого проактивного
группового сообщения определённой категории вызывает единую функцию
`resolve_thread_id(project_id, category)`:
1. Есть строка `ProjectTopicSetting` для (`project_id`, `category`) → берётся её
   `thread_id`.
2. Иначе → берётся `Project.default_thread_id`.
3. Если и он `null` (чат без топиков, либо `/setup_registration` ни разу не был вызван
   внутри топика) → параметр `message_thread_id` в вызове Bot API не передаётся,
   сообщение уходит в топик по умолчанию чата.

Сообщения, являющиеся **прямым ответом на команду**, вызванную пользователем в
конкретном топике, вместо резолвинга по категории просто повторно используют
`message_thread_id` входящего апдейта — отвечают туда же, откуда вызвали команду.
Так работает `/all` (раздел 4.2): категорийная схема выше на него не распространяется.

**Настройка топика админом.** Команда `/set_topic <category>` (только `role=admin`),
вызванная **внутри топика**, который должен принимать сообщения этой категории:
- `category` — один из `events`/`money_collections`/`general`/`rights` (`rights` —
  топик регулирования прав, см. 3.7; при некорректном значении бот отвечает списком
  допустимых);
- backend берёт `message_thread_id` из апдейта команды и делает upsert строки
  `ProjectTopicSetting(project_id, category, thread_id)`;
- бот подтверждает: «Мероприятия теперь будут анонсироваться в этом топике» (текст
  зависит от категории).

Если чат не форум-группа (нет топиков), `/set_topic` отвечает пояснением, что команда
не применима — привязка топика не имеет смысла без топиков.

Порядок проверок в `/set_topic` (и `/unset_topic`): сначала существование проекта
и `role=admin`, только потом разбор категории. Иначе не-админ, вызвавший команду
без категории или с некорректной, получал бы список допустимых категорий вместо
отказа по правам, а сам отказ видел бы только после подстановки верной категории.

**Снятие привязки.** Команда `/unset_topic <category>` (только `role=admin`) удаляет
строку `ProjectTopicSetting(project_id, category)`, категория `category` — один из
`events`/`money_collections`/`general`/`rights` (тот же список, что и у `/set_topic`,
при некорректном значении — то же сообщение со списком допустимых). В отличие от
`/set_topic`, не требует вызова именно из отвязываемого топика — категория передаётся
текстом, бот и так знает, какую строку удалять, физическое присутствие в топике не
нужно. Выполняется сразу, без подтверждения (симметрично `/set_topic`). Единственный
эффект, который стоит держать в голове: `/unset_topic rights` немедленно отключает
гейт admin-команд, описанный в 3.7 (переходит в состояние «топик не назначен» — см.
там же), — это осознанное следствие общего правила, отдельного предупреждения бот не
показывает.

### 3.6 Меню команд бота (подсказки по `/`)

Список команд, который Telegram показывает пользователю при вводе `/` в чате с ботом
(автодополнение), — это не список зарегистрированных хендлеров aiogram, а отдельная
настройка на стороне Bot API. Без явного вызова `Bot.set_my_commands()` этот список
пуст, даже если сами команды исправно работают.

**Что нужно сделать:**
1. Вызвать `bot.set_my_commands(commands, scope=...)` при старте приложения (режим
   `bot+api`, см. 3.1) — например, в `create_bot`/точке входа рядом с созданием
   `Bot`/`Dispatcher` (`src/meetup_bot/bot/__init__.py`, `src/meetup_bot/app.py`), до
   начала обработки апдейтов.
2. Команды делятся на группы по scope (`aiogram.types.BotCommandScope*`), т.к.
   набор отличается для приватного чата и группы:
   - `BotCommandScopeAllPrivateChats` — `start` (без payload — подсказка, см. 4.1);
     команды открытия Mini App (`new_event`, далее `edit_event`, `cancel_event` —
     этап 2, разделы 3.8 и 4.3) добавляются сюда же по мере реализации;
   - `BotCommandScopeAllGroupChats` — `setup_registration`, `set_topic`,
     `unset_topic`, `all`, `members`, `remove_member`, `add_admin`, `remove_admin`
     (все — groupspecific, см. 4.1–4.2).
   Если когда-нибудь понадобится различать обычных участников и админов —
   `BotCommandScopeChatAdministrators`/`BotCommandScopeChatMember` для конкретного
   `chat_id`, но пока такой необходимости нет, набор в группе один для всех.
3. Каждая команда — короткое описание на русском (лимит Bot API — 256 символов),
   например:
   - `start` — «Зарегистрироваться по ссылке из чата»;
   - `setup_registration` — «Настроить бота в этом чате / переназначить топик»;
   - `set_topic` — «Привязать топик к категории сообщений»;
   - `unset_topic` — «Снять привязку категории от топика»;
   - `all` — «Позвать всех зарегистрированных участников»;
   - `members` — «Список участников проекта»;
   - `remove_member` — «Удалить участника из проекта»;
   - `add_admin` — «Назначить администратора проекта»;
   - `remove_admin` — «Понизить со-администратора до участника».
4. При добавлении/переименовании команды в будущем — обновлять и хендлер, и список в
   `set_my_commands`, иначе подсказки разъедутся с реальным поведением бота.

Разбивку между личным чатом и группой стоит сделать через два отдельных вызова
`set_my_commands()`, а не общий scope `default` — иначе, например, `/start` будет
подсказываться и в группе, где он не работает (см. 4.1: `/start` зарегистрирован
только на `F.chat.type == "private"`), и наоборот, групповые команды — в личке.

Отдельно от `set_my_commands` при старте приложения выставляется **глобальная
кнопка-меню** `setChatMenuButton` (без `chat_id`) → `MenuButtonWebApp` на домашний
экран-хаб Web App (раздел 3.8). Это заменяет раскрытие `PRIVATE_COMMANDS` под самой
кнопкой-меню в личке; автодополнение команд по `/` в поле ввода сохраняется, поэтому
`PRIVATE_COMMANDS` в `set_my_commands` регистрируются как прежде.

### 3.7 Топик регулирования прав (`rights`) и гейт admin-команд

**Мотивация.** Изменение прав (кто админ, кого исключить) и просмотр состава — это
чувствительные действия. Ролевая проверка (`role=admin`/`role=owner`) уже не пускает
рядового участника их вызвать, но ничего не мешает вызвать их из любого топика на
виду у всех, включая уже видимые всем inline-кнопки подтверждения (см. комментарий в
`admin_commands.py` про ограничение Bot API — бот не умеет показывать кнопки
выборочно). Выделенный топик прав — организационная изоляция: обсуждение/подтверждение
таких действий физически не попадается на глаза обычным участникам чата, читающим
общий/тематические топики.

**Назначение топика.** Топик прав — обычный `ProjectTopicSetting` с
`category=rights` (раздел 2.2), назначается существующей командой `/set_topic rights`,
вызванной внутри выбранного топика (правила — как у любой другой категории, раздел
3.5), снимается — `/unset_topic rights` (см. выше). Никакого отдельного механизма
назначения не вводится — переиспользуется уже существующий паттерн.

**Гейт.** Следующие команды отказываются выполняться, если вызваны **не** из топика,
назначенного под `rights` (как только он назначен):
- `/members`
- `/remove_member`
- `/add_admin`
- `/remove_admin` (см. 4.1)

При отказе бот отвечает сообщением, что команда доступна только из топика прав.
Инлайн-кнопки подтверждения (выбор человека → подтверждение), которые эти команды
показывают, физически рождаются в том же сообщении/топике, что и сама команда —
отдельной проверки на клик не требуется.

**Исключения из гейта — `/set_topic` и `/setup_registration`.** Обе команды тоже
меняют административно значимое состояние проекта, но гейтить их топиком `rights`
структурно невозможно или бессмысленно:
- `/set_topic <category>` обязана вызываться **внутри назначаемого** топика (в т.ч.
  когда назначают сам топик `rights`) — если бы она одновременно требовала вызова
  из топика `rights`, это было бы физически невыполнимо (нельзя быть в двух топиках
  разом), кроме случая `category=rights`, где это совпадает по построению;
  `/unset_topic` по той же причине тоже исключена, хоть и не привязана к конкретному
  топику физически — она часть той же пары команд;
- `/setup_registration` может быть первым вызовом в новом чате, когда проекта (и,
  соответственно, топика `rights`) ещё не существует — гейтить нечем (bootstrap).

**Fallback: топик `rights` не назначен.** Гейт применяется только если для проекта
есть строка `ProjectTopicSetting(category=rights)`. Пока её нет (новый проект,
`rights` ни разу не привязывали, либо его отвязали через `/unset_topic rights`) —
`/members`/`/remove_member`/`/add_admin`/`/remove_admin` работают откуда угодно, как
до введения этой фичи, чистая ролевая проверка. Это тот же принцип, что и у
`resolve_thread_id` (раздел 3.5) для остальных категорий: отсутствие настройки — не
отказ, а прозрачный fallback к менее строгому поведению.

**Fallback: чат без топиков.** В нефорумном чате топик `rights` в принципе не может
существовать (`message.chat.is_forum == false`) — гейт для такого чата не действует
никогда, `/members`/`/remove_member`/`/add_admin`/`/remove_admin` работают как раньше.
Не превращать бота в неработоспособного для чатов без форум-режима — приоритетнее
строгости гейта.

**Восстановление, если топик прав удалён/потерян.** `/set_topic` не входит в гейт
(см. выше), поэтому владелец в любой момент может назначить `rights` заново из
любого другого топика — отдельного механизма восстановления не требуется.

**Общий принцип на будущее.** Правило не ограничивается перечисленными выше четырьмя
командами: любая будущая admin-команда, которая меняет права участников или состав
проекта (а не просто настройки/контент), обязана попадать под тот же гейт — вызываться
только из топика `rights`, с тем же fallback-поведением при отсутствии назначенного
топика или в чатах без топиков. Это касается, например, любых будущих команд
управления со-организаторами мероприятий (раздел 4.3) в части изменения именно прав, а
не самого мероприятия.

### 3.8 Ограничения Telegram Web App и точки входа в Mini App

Ограничения платформы, из которых вытекает, как и откуда открываются экраны Web App
(домашний экран-хаб, создание/редактирование мероприятия, постфактум-корректировка
RSVP, пороги проекта).

**Публичный HTTPS.** `web_app`-кнопку Telegram-клиент откроет только по публичному
`https://` с валидным (не самоподписанным) сертификатом — та же причина, по которой
выбран Tailscale Funnel (раздел 1.3). Отдельного адреса не нужно: Mini App раздаётся
с того же origin, что и вебхук бота, под путём `/app` (раздел 3.1, компонент 3;
`app._mount_webapp`). Базовый URL Mini App — в конфиге приложения (`public_base_url`);
без него бот не строит `web_app`-кнопки. Для inline-`web_app`-кнопок домен в BotFather
настраивать не требуется (годится любой URL этого origin); настройка приложения в
BotFather нужна только для прямых ссылок `t.me/<bot>/<app>?startapp=…` и attachment
menu — в MVP не используются.

**Типы кнопок, открывающих Mini App, и где каждая работает:**

| Способ | Где работает | Контекст в URL |
|---|---|---|
| `InlineKeyboardButton(web_app=WebAppInfo(url))` | личка, группы, супергруппы (не каналы) | любой URL на каждое сообщение |
| `KeyboardButton(web_app=…)` (reply-клавиатура) | только личка | любой URL |
| кнопка-меню (`setChatMenuButton` → `MenuButtonWebApp`) | личка (в группе кнопка-меню = список команд) | URL фиксированный, без контекста — проект разрешает сам экран |
| ссылка `t.me/<bot>/<app>?startapp=PARAM` | любой чат как URL-ссылка | `PARAM` → `start_param` (нужна регистрация app в BotFather) |

**Решение проекта: все точки входа в Mini App — из приватного чата с ботом.**
Две группы точек входа, обе только в личке:

- **Постоянная кнопка-меню** слева от поля ввода (`setChatMenuButton` →
  `MenuButtonWebApp`) → **домашний экран-хаб** Web App (см. ниже);
- **команды под конкретную задачу** — `/new_event`, `/edit_event`, экран
  корректировки RSVP, экран порогов; бот отвечает сообщением с
  `InlineKeyboardButton(web_app=…)` с уже подставленным контекстом.

`web_app`-кнопок под групповыми сообщениями (в т.ч. под анонсом мероприятия) нет.
Причины:

1. inline-кнопку под сообщением в группе видят **все** участники чата, выборочно
   скрыть нельзя (то же ограничение Bot API, что в разделах 3.7 и 4.3) — иначе
   пришлось бы проверять право уже на клик и показывать отказ посторонним;
2. при открытии Mini App из кнопки в группе `initData` **не содержит `chat_id`**
   (только `chat_type` и непрозрачный `chat_instance`) — вывести из него проект
   невозможно. В личке бот либо сам знает членство пользователя и кладёт
   `project_id` (= `invite_payload`) в URL кнопки-ответа на команду (если проектов
   несколько — сначала инлайн-выбор проекта, потом кнопка), либо проект разрешает
   сам домашний экран (см. ниже).

**Домашний экран-хаб и постоянная кнопка-меню (входят в MVP).**

- **Что это.** Стартовый экран Web App: кто пользователь, в каких он проектах, и —
  под каждым проектом — список его мероприятий (всё, кроме отменённых) и переход
  «создать мероприятие». Тап по мероприятию открывает **экран мероприятия**: поля
  (когда / где / о чём / бюджет / места / организаторы), сводка RSVP (сколько
  участвует и не участвует, статус самого пользователя), кнопки «Участвую» /
  «Не участвую» (та же самоотметка, что под анонсом, — задача 2.6, не форма) и
  переход на анонс в групповом чате. У организатора мероприятия (или создателя /
  админа, если организатор не назначен) на этом экране добавляются действия
  «Редактировать» (открывает форму редактирования, задача 2.7) и «Отменить» (та же
  логика, что команда `/cancel_event`, задача 2.8) — в собственной шапке экрана,
  т.к. Telegram не даёт Web App надёжного меню действий для отдельного под-экрана.
- **Чего на хабе нет.** Статистики посещаемости и геймификации — полноценный
  «Личный кабинет» остаётся в backlog (раздел 5) и, когда появится, ляжет разделом
  того же хаба. Смены RSVP за другого участника (постфактум-корректировка) — это
  отдельный экран организатора, задача 3.1.
- **Разбивка на PR.** Хаб делается тремя PR-размерными подпунктами (`TASKS.md`:
  2.9.1 кнопка-меню + хаб + список мероприятий; 2.9.2 экран мероприятия + RSVP из
  Web App; 2.9.3 отмена мероприятия из Web App). Логику RSVP (2.6) и отмены (2.8)
  для переиспользования из `/api/*` выносят в сервисы, поведение команд бота при
  этом не меняется.
- **Кнопка-меню — глобальная.** `setChatMenuButton` вызывается **без** `chat_id`
  (одна на бота) при старте приложения, рядом с `set_my_commands` (раздел 3.6),
  на фиксированный URL хаба без параметров. Per-chat вариант
  (`setChatMenuButton(chat_id=…)` после `/start` с точным `project_id`) в MVP не
  используется — лишнее состояние на каждого пользователя ради экономии одного
  шага выбора проекта.
- **Разрешение проекта — на стороне экрана.** URL хаба контекста не несёт, поэтому
  хаб при загрузке берёт `initData`, запрашивает у бэкенда список активных
  `ProjectMembership` пользователя (валидация — та же dependency, что и для
  остальных `/api/*`, раздел 2.3 / 3.2) и:
  - 0 проектов → состояние «вы не зарегистрированы» + кнопка-ссылка на deep-link
    регистрации (то же, что `403 not_registered`, раздел 3.2, п. 4);
  - 1 проект → сразу хаб этого проекта;
  - несколько → хаб показывает все проекты пользователя секциями (у каждой — свой
    список мероприятий и переход «создать мероприятие»); отдельного экрана выбора
    проекта нет. Формы и экраны мероприятий открываются уже с `project`
    конкретной секции в URL.
- **Кнопка-меню в личке заменяет список команд по `/`** (раздел 3.6): после
  `setChatMenuButton` → `MenuButtonWebApp` та же кнопка перестаёт раскрывать
  `PRIVATE_COMMANDS`. Команды `/new_event` и т.д. продолжают работать по вводу
  вручную и остаются в `set_my_commands` (автодополнение по `/` в поле ввода
  никуда не девается) — теряется только их список под самой кнопкой-меню. Это
  осознанный размен: постоянная точка входа в Web App важнее, чем список из
  двух-трёх команд под кнопкой.
- **BotFather.** Домен для `MenuButtonWebApp` настраивать не требуется — как и для
  inline-`web_app`-кнопок (см. «Публичный HTTPS» выше), годится любой URL этого
  origin.
- **Деградация.** На клиентах старше Telegram 7.0 кнопка-меню Web App не
  поддерживается — там остаётся список команд по `/`, входа в хаб нет, но команды
  (`/new_event` и др.) работают как обычно.

**Состав `initData`.** Всегда есть `user`, `auth_date`, `hash`; полный объект `chat`
приходит только из attachment menu. Поэтому `project_id` — отдельный параметр запроса,
бэкенд сверяет его с `ProjectMembership` пользователя (раздел 3.2, п.4). Проверяется
именно `hash` (HMAC), поле `signature` в HMAC-проверку не входит.

**Направление Mini App → бэкенд.** `Telegram.WebApp.sendData()` доставляет данные
ботом-апдейтом только для Mini App, открытого из reply-клавиатуры — в проекте не
используется. Все формы шлют данные через `POST /api/*` с заголовком
`X-Telegram-Init-Data` (раздел 3.2).

**Жизненный цикл.** `initData` фиксируется при запуске Mini App; бэкенд проверяет
`auth_date` не старше 24 часов. На ответ `401` от бэкенда фронтенд просит переоткрыть
Mini App. Клиенты старше Telegram 7.0 `web_app`-кнопки не поддерживают — деградация
мягкая (кнопка есть, при ошибке — понятный текст).

**Фронтенд-стек.** Ограничения по версиям зависимостей Web App
(`@telegram-apps/telegram-ui` пинит React на 18; SDK — `@tma.js/sdk`) —
операционные, живут в `webapp/README.md` и `docs/TASKS.md`, здесь не дублируются.

## 4. Функциональная спецификация MVP

### 4.1 Регистрация и участники

**Экраны/команды:**
- Групповой чат: пост с текстом-приглашением и inline URL-кнопкой
  «Зарегистрироваться» → `t.me/<bot>?start=<invite_payload>` (закрепление поста —
  вручную, силами администратора чата, см. 3.3, шаг 3).
- Приватный чат с ботом:
  - `/start <invite_payload>` → регистрация (см. 3.3), приветственное сообщение.
  - `/start` без payload (если человек просто открыл бота напрямую) → сообщение
    «Чтобы зарегистрироваться в проекте, перейдите по ссылке из поста
    регистрации в вашем групповом чате».
- Команды админа (только `role=admin`, если не указано иное); `/members`,
  `/remove_member`, `/add_admin`, `/remove_admin` дополнительно гейтятся топиком
  `rights`, если он назначен для проекта (см. 3.7):
  - `/members` — список зарегистрированных участников проекта (для сверки).
  - `/remove_member` → открывает Web App-форму (список участников с чекбоксом/кнопкой
    удаления — по факту это точечный выбор одного человека, но UI переиспользует общий
    компонент выбора людей) или, как упрощение MVP, инлайн-список кнопок «Удалить
    <имя>» с подтверждением — решается на этапе реализации по вкусу, поле `status`
    переводится в `removed`, `removed_by`/`removed_at` заполняются. Владельца (`role=owner`)
    выбрать нельзя — не входит в список кандидатов.
  - `/add_admin` (только `role=owner`) — назначение со-админа из уже зарегистрированных
    участников с `role=member` (аналогично `/remove_member`, инлайн-выбор из списка с
    подтверждением).
  - `/remove_admin` (только `role=owner`) — обратная операция: понижение роли уже
    назначенного со-админа (`role=admin`) обратно до `role=member`; участник остаётся
    в проекте, удаляются только права. Кандидаты — активные `role=admin` (владелец,
    как и в `/remove_member`, в список не попадает — его нельзя ни понизить, ни
    удалить). Тот же UI-паттерн выбор → подтверждение.
  - `/set_topic <category>` — привязка топика группового чата к категории сообщений
    бота (`events`/`money_collections`/`general`/`rights`), вызывается внутри целевого
    топика (см. 3.5, 3.7).
  - `/unset_topic <category>` — снятие привязки категории от топика (см. 3.5), из
    любого места, без требования физического присутствия в отвязываемом топике.
  - `/settings [<параметр> <значение>]` — просмотр и изменение порогов
    `ProjectSettings` (`reminder_days_threshold`, `missed_events_escalation_count`,
    `reminder_send_hour`, `timezone`; см. 2.3, 3.4). Без аргументов — список
    текущих значений; с аргументами — валидация и сохранение. Не гейтится
    топиком `rights` (меняет пороги, не состав участников).

### 4.2 Тегание

- Команда `/all` в групповом чате: бот подтягивает всех `ProjectMembership(status=active)`
  этого `project_id` (по `tg_chat_id` группы), собирает упоминания по `username`, если
  есть, либо text-mention (`tg://user?id=...`) для тех, у кого приватный юзернейм —
  так тегаются и те, кто скрыл `@username` в настройках приватности, при условии, что
  зарегистрирован. Разбивка на несколько сообщений, если участников много (лимит длины
  сообщения Telegram). Ответ уходит в тот же топик, откуда вызвали команду (раздел
  3.5, "прямой ответ на команду") — не резолвится по категории `general`.
  Троттлинг — не чаще раза в `ProjectSettings.all_command_throttle_seconds` секунд
  на проект (раздел 2.3; 6.1).
- Точечный выбор части людей (для форм мероприятия/сбора) — не отдельная фича, а
  переиспользуемый UI-компонент Web App: список участников проекта с чекбоксами,
  кнопка «выбрать всех/снять всех».

### 4.3 Мероприятия

**Создание (Web App):**
1. В приватном чате с ботом командой `/new_event` участник получает `web_app`-кнопку,
   открывающую форму создания (все точки входа в Mini App — из лички, см. раздел 3.8).
   Если участник состоит в нескольких проектах — бот сначала предлагает инлайн-выбор
   проекта, затем присылает кнопку с уже подставленным `project_id`.
2. Форма (один экран, поля сверху вниз):
   - Дата и время начала (date/time picker) — обязательное;
   - Дата и время окончания (`ends_at`) — опциональное, для мероприятий на несколько
     дней; если не заполнено, эффективным окончанием считается дата начала;
   - Место — текстовое поле, обязательное;
   - Описание — многострочное текстовое поле, обязательное;
   - Бюджет с человека — числовое поле, опциональное;
   - Лимит мест — числовое поле, опциональное; трактуется как «мягкий» ориентир
     (сколько человек нужно собрать), а не жёсткий потолок — см. блок «RSVP» ниже;
   - Со-организаторы — список участников проекта с чекбоксами (по умолчанию отмечен
     создатель). В отличие от точечного выбора людей в других формах, создатель
     **может** снять чекбокс и с себя — тогда мероприятие публикуется вообще без
     организатора (для лёгких встреч вроде вечерней прогулки, см. `CONCEPT.md`,
     раздел 3); права редактирования и постфактум-корректировки RSVP в этом случае
     проверяются по `Event.created_by` и по `role=admin`, а не по `EventCoOrganizer`.
3. Кнопка «Опубликовать» → `POST /api/events` → создаёт `Event` + строки
   `EventCoOrganizer` (ноль или больше строк).
4. Backend от имени бота публикует анонс в группу, в топик, определённый для категории
   `events` (`resolve_thread_id(project_id, "events")`, раздел 3.5): текст со всеми
   полями + два inline-кнопки «✅ Участвую» / «❌ Не участвую». `announcement_message_id`
   сохраняется (последующее редактирование/отмена — `editMessageText` по этому
   `message_id`, топик знать заново не нужно, Bot API адресует правку по `message_id`).

**RSVP (обычные inline-кнопки бота), живое обновление анонса:**
- Нажатие «Участвую»/«Не участвую» под анонсом → `EventRSVP` upsert по
  (`event_id`, `user_id`) с `updated_by = user_id` (самоотметка). Повторное нажатие
  меняет статус (переключатель, а не накопление записей).
- Каждое такое изменение сразу правит текст анонса (`editMessageText` по
  `announcement_message_id`):
  - счётчик подтвердивших: «Участвует: N», либо «Участвует: N/seats_limit», если
    лимит мест задан. Лимит — мягкий: N может его превысить (например, «17/15»), и
    при N ≥ seats_limit к счётчику добавляется пометка, что цель набрана. RSVP по
    достижении лимита не блокируется — кнопки продолжают работать (лимит говорит,
    сколько человек нужно собрать для проведения мероприятия, а не ставит потолок);
  - список никнеймов подтвердивших (`@username`, либо text-mention/имя для тех, у
    кого приватный юзернейм — аналогично `/all`, раздел 4.2);
  - список никнеймов отказавшихся («Не участвует: K» + перечисление в том же
    формате).
  Третья группа — активные участники проекта, ещё не нажавшие ни одну кнопку
  («не прочитал / думает»), — в анонсе отдельно не выводится (вычислима как
  «реестр минус обе группы»); явно показываются только «участвует» и «не участвует».
  Callback-ответ на нажатие — короткое всплывающее подтверждение статуса, без
  отдельного сообщения в чат.
- Тот же upsert, но с `updated_by`, отличным от `user_id` (постфактум-правка чужого
  RSVP организатором/создателем/админом) — отдельный сценарий, описан в разделе 4.4.

**Редактирование/отмена:**
- Редактирование — команда `/edit_event` в приватном чате с ботом: бот присылает
  список мероприятий, где у вызвавшего есть право (организатор/со-организатор по
  `EventCoOrganizer`, либо, если строк нет, — создатель мероприятия или админ
  проекта), у каждого — `web_app`-кнопка, открывающая форму редактирования (те же
  поля, предзаполненные). Право проверяется ещё раз на бэкенде при сохранении.
  Кнопки «Редактировать» под анонсом в группе нет намеренно (раздел 3.8): inline-
  кнопку под групповым сообщением видят все, выборочно не спрятать, а из группы
  `initData` не даёт контекст проекта. Все точки входа в Mini App — из лички.
- Сохранение изменений → обновление `Event`, редактирование текста анонса
  (`editMessageText` по `announcement_message_id`), и рассылка личных уведомлений
  всем, у кого `EventRSVP.status = going`, о том, что изменилось.
- Отмена — действие в той же форме редактирования либо команда `/cancel_event` в
  личке → `Event.status = cancelled`, анонс помечается «Мероприятие отменено», всем
  подтвердившим — личное уведомление.

### 4.4 Учёт посещаемости и напоминания

Отдельного постфактум-шага «отметить явку» нет (см. `CONCEPT.md`, раздел 3): факт
явки — это финальное состояние `EventRSVP` на момент автоматической финализации
мероприятия воркером (раздел 3.4, п.1).

**Постфактум-корректировка RSVP (Web App или инлайн-список):**
1. Организатор/со-организатор (либо создатель/админ, если организатора нет) может в
   любой момент — до финализации мероприятия или после неё — открыть экран со
   списком участников проекта и текущим статусом RSVP каждого (переиспользует
   компонент выбора людей, раздел 4.2), и поменять чужой статус (например, отметить
   «не участвует» тому, кто нажал «участвую», но не пришёл, либо, наоборот, добавить
   пришедшего без RSVP).
2. Каждое такое изменение — тот же `EventRSVP` upsert, что и при самоотметке (раздел
   4.3), но с `updated_by` = id корректирующего. Правки до финализации мероприятия
   просто меняют текущее состояние (и, как обычная RSVP, сразу отражаются в анонсе);
   правки после финализации дополнительно пересчитывают `last_attended_at`/
   `consecutive_missed_events` точечно для скорректированного участника (раздел 3.4,
   п.1, последний абзац).
3. Отдельного напоминания «заполните чек-лист» не требуется: буфер на правки — это
   и есть время до полуночи следующего дня после `ends_at`/`starts_at` (раздел 3.4,
   п.1), когда мероприятие ещё не финализировано.

**Личные напоминания «давно не виделись» и эскалация** — полностью описаны в 3.4,
это фоновый процесс, отдельного UI кроме самого сообщения в ЛС не требует. Текст
сообщения участнику: «Ты не был(а) на встречах уже N дней. Ближайшее мероприятие:
<название/дата> — <ссылка на анонс/бот-кнопка RSVP>» либо, если ближайшего
мероприятия нет: «...загляни в чат, вдруг что-то планируется».

Статистика посещаемости нигде в MVP не выводится публично (ни лидерборда, ни
профиля с цифрами, доступного другим участникам) — это сознательное ограничение
из `CONCEPT.md`.

## 5. Backlog (пост-MVP)

Ниже — перенос backlog-раздела `CONCEPT.md` с пометкой, как каждая фича ляжет на
описанную архитектуру. Детальной проработки экранов на этом этапе не делается.

- **Сбор денег на общую покупку.** Сущности `MoneyCollection`,
  `MoneyCollectionParticipant`, `PaymentProfile`, `PaymentConfirmation` уже заложены
  в модель данных (раздел 2). Создание/редактирование — по аналогии с мероприятиями,
  через Web App (форма с выбором участников чекбоксами, суммой, опциональной привязкой
  к `event_id`). Уведомление и кнопка «Оплатил» — обычные inline-кнопки бота (по
  аналогии с RSVP), канал (ЛС/группа) выбирает создатель при создании сбора; при выборе
  «группа» топик определяется как для категории `money_collections` (раздел 3.5).
- **Прикрепление изображений** к формам мероприятия/сбора. Технически — поле
  file upload в Web App-форме, загрузка через Telegram Bot API (`sendPhoto`/получение
  `file_id`) либо через отдельный object storage (S3-совместимый, например Cloudflare
  R2, если понадобится хранить вне Telegram). Потребует нового поля
  (`photo_file_id`/`photo_url`) на `Event`/`MoneyCollection`.
- **Опрос впечатлений после мероприятия.** Отдельная сущность (например,
  `EventFeedback`: `event_id`, `user_id`, `text`/оценка), отдельный триггер в
  планировщике (через X часов после мероприятия — независимо от финализации явки),
  доставка — простое сообщение в ЛС с текстовым вводом или короткой Web App-формой.
  Не влияет на `last_attended_at`/эскалацию.
- **Режим паузы/отпуска.** Команда боту (`/pause`, `/unpause`) в приватном чате,
  добавляет поле `is_paused`(+ `paused_until`, опционально) на `ProjectMembership`.
  Планировщик (раздел 3.4, шаги 2–3) просто пропускает участников с `is_paused=true`.
  Не исключает из `/all` и общих опросов.
- **Личный кабинет.** Дополнительный раздел той же Web App (не новый сервис) —
  экран со статистикой участника по данным `EventRSVP`, доступный
  только самому пользователю (авторизация та же — через `initData`). Ложится
  разделом домашнего экрана-хаба, который входит в MVP как навигационный хаб без
  статистики (раздел 3.8); backlog здесь — именно статистика и геймификация, а не
  сам экран и не кнопка-меню.
- **Автоматизация ротации ответственных.** Логика в App-сервисе/планировщике:
  очередь кандидатов на организатора следующего мероприятия по какому-то правилу
  (например, кто дольше всех не организовывал), уведомление в чат/ЛС с предложением
  создать мероприятие. Не требует новых сущностей верхнего уровня, возможно поле
  `last_organized_at` на `ProjectMembership`.
- **Self-service онбординг новых проектов.** Замена ручного/полутехнического
  создания `Project` (см. 3.3, шаг 2) на UI-мастер (Web App или отдельная
  посадочная страница) для стороннего админа: добавление бота в свою группу →
  форма создания проекта и первичных настроек без участия разработчика. Затрагивает
  преимущественно UX создания `Project`/`ProjectSettings`, схема данных уже готова.
- **Передача владения проектом (`/transfer_owner`).** Сейчас `role=owner`
  невозможно ни понизить (`/remove_admin` его не касается, раздел 4.1), ни удалить
  (`/remove_member` явно защищает владельца) — если единственный владелец пропадёт
  (выйдет из чата/потеряет доступ), в проекте никогда не появится новый владелец, а
  значит и новый со-админ через `/add_admin` (команда только для `role=owner`).
  Осознанный пробел MVP: проработка отложена — нужна модель подтверждения с обеих
  сторон (текущий владелец инициирует, новый — подтверждает), это отдельная фича,
  не довесок к гейту прав (раздел 3.7).

## 6. Нефункциональные требования

### 6.1 Безопасность

- **Валидация `initData`** на каждый запрос Web App → API — обязательна и не
  кэшируется между запросами (см. раздел 3.2). Секрет — токен бота, никогда не
  передаётся на фронтенд.
- **Изоляция данных между проектами (tenant isolation).** Абсолютно все запросы к
  данным мероприятий/участников/сборов на бэкенде фильтруются по `project_id`,
  который выводится из проверенного контекста (chat_id апдейта от Telegram или
  `project_id`, подтверждённый по `ProjectMembership` пользователя из `initData`), а
  не из значения, присланного клиентом напрямую без проверки принадлежности. Ни один
  SQL-запрос к «многотенантным» таблицам не должен идти без условия по `project_id`.
- **Секреты.** Токен бота, строка подключения к БД — только в переменных окружения /
  `.env`, никогда не в репозитории; на проде — через Docker secrets или переменные
  окружения контейнера, доступ к `.env` файлу только у деплоящего.
- **Права ролей.** Действия админа (изменение `ProjectSettings`, удаление из реестра,
  назначение со-админов) — серверная проверка `role=admin` по `ProjectMembership`, не
  полагаться на скрытие кнопки в UI. Дополнительно для команд, меняющих права/состав
  (`/members`, `/remove_member`, `/add_admin`, `/remove_admin`) — гейт по топику
  `rights`, если он назначен (раздел 3.7); проверка тоже на бэкенде, не на UI.
- **Rate limiting / anti-spam** — ограничение частоты `/all` на проект: интервал
  задаётся `ProjectSettings.all_command_throttle_seconds` (раздел 2.3, по умолчанию
  180 секунд), чтобы не заспамить группу и не словить лимиты Telegram на отправку
  сообщений.

### 6.2 Логирование и мониторинг

- Структурированные логи (JSON) в stdout контейнера — этого достаточно при таком
  масштабе, отдельный ELK/Grafana не нужен. Ротация — штатными средствами Docker
  (`max-size`/`max-file` в конфиге логирования).
- Обязательно логировать: ошибки отправки сообщений Telegram (в т.ч. `403 bot was
  blocked by the user` — признак, что человек заблокировал бота, стоит помечать это
  на `User`/`ProjectMembership`, чтобы не долбить в напоминаниях), ошибки валидации
  `initData`, необработанные исключения обработчиков.
- Простой health-check эндпоинт (`GET /health`) для внешнего аптайм-монитора
  (например, бесплатный UptimeRobot/healthchecks.io) — минимальный сигнал «бот жив».
- Cron-задача планировщика логирует старт/итог каждого прохода (сколько напоминаний
  отправлено) — по этим логам легко вручную сверить, что механика работает, на
  начальном этапе без БД-дашборда.

### 6.3 Бэкапы

- Ежедневный `pg_dump` по cron на самом сервере (домашнем Proxmox-хосте или VPS —
  в зависимости от выбранного варианта из раздела 1.3), хранение последних N (например,
  7) дневных копий локально + выгрузка последней копии во внешнее хранилище (например,
  ежедневная заливка в приватный облачный сторадж/бакет — S3-совместимый, недорогой)
  на случай потери самого сервера. При домашнем хостинге внешняя копия обязательна ещё
  сильнее, чем на VPS (см. риски в разделе 1.3) — локальный диск того же физического
  железа не защищает от его отказа.
- Периодическая (хотя бы раз в квартал) ручная проверка, что бэкап реально
  разворачивается — иначе бэкап есть только «на бумаге».

## 7. Этапы реализации (roadmap)

Порядок разработки — от простого фундамента к полной картине, каждый этап даёт
проверяемый работающий кусок функциональности.

**Этап 1. Реестр участников и мультитенантный каркас.**
Схема БД (раздел 2) и миграции; обработка добавления бота в группу
(`my_chat_member` → создание `Project`/`ProjectSettings`/первого админа); команда
`/start <payload>` с регистрацией; `/setup_registration` с захватом топика по
умолчанию (раздел 3.3/3.5); пост с deep-link кнопкой (закрепление — вручную
администратором); `/all`;
базовые админ-команды (`/members`, удаление участника, `/set_topic`). Результат: можно
вручную завести проект-друзей, все зарегистрироваться, потегать всех разом, при
необходимости раскидать сообщения бота по нужным топикам.

**Этап 2. Мероприятия: создание и RSVP.**
Web App-заготовка (Vite + React + Telegram SDK, деплой как статика), кнопки открытия
Mini App из приватного чата (раздел 3.8): команды под задачу с контекстом проекта в
URL плюс постоянная глобальная кнопка-меню на домашний экран-хаб (навигационный, без
статистики; проект разрешается на стороне экрана по `initData`), форма создания
мероприятия (включая опциональные со-организаторов и `ends_at` — мероприятие может
быть без организатора и на несколько дней), эндпоинт создания, публикация анонса с
inline-кнопками «участвую/не участвую» и живым обновлением счётчика и двух списков
(участвуют / отказались) при каждом нажатии, редактирование/отмена мероприятия
(с проверкой прав по `EventCoOrganizer` либо, если организатора нет, по
`created_by`/`role=admin`)
с уведомлением подтвердивших. Результат: организатор (или создатель мероприятия без
организатора) полностью ведёт мероприятие через бота от анонса до отмены/
редактирования, а участники в любой момент видят актуальный список в самом анонсе.

**Этап 3. Постфактум-корректировка RSVP.**
Экран (Web App или инлайн-список) для организатора/создателя/админа со списком
участников и их текущим статусом RSVP, возможность поменять чужой статус (упсерт
`EventRSVP` с `updated_by`, отличным от `user_id`). Результат: ошибочные самоотметки
можно поправить постфактум — данные для будущих напоминаний и для автоматической
финализации явки (Этап 4) собираются без отдельного шага «отметить явку».

**Этап 4. Напоминания, финализация явки и эскалация.**
Worker-процесс с APScheduler, все три прохода из раздела 3.4 (финализация явки по
списку `EventRSVP` в полночь следующего дня после окончания мероприятия — сброс
`last_attended_at`/`consecutive_missed_events`, личное напоминание участнику,
эскалация организатору/админу при повторных пропусках), настройки порогов через
`ProjectSettings` + минимальный UI/команды для админа, чтобы их менять (например,
через Web App-экран настроек проекта). Результат: MVP полностью замыкает цикл
«RSVP → финализация → напоминание → эскалация», ради которого всё затевалось.

**Этап 5. Полировка.**
Обработка граничных случаев (бот заблокирован пользователем, повторные клики по
RSVP, пустые мероприятия без единого RSVP при финализации явки, гонки при
одновременном редактировании двумя со-организаторами), тексты сообщений,
health-check и логирование по разделу 6.2, настройка бэкапов по разделу 6.3, чистый
прод-деплой через Docker Compose (домашний Proxmox-сервер + Tailscale Funnel, раздел
1.3) с настроенным TLS. Результат: система, которую не
страшно оставить работать без присмотра.
