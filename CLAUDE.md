# Правила работы над проектом

## Разработка через Pull Request

Весь код в `main` попадает только через Pull Request в
`git@github.com:asutenshi/meetup-bot.git`. Прямые коммиты в `main` не делаются.

- Одна подзадача из [`docs/TASKS.md`](./docs/TASKS.md) = одна ветка = один PR.
  Не смешивать несколько подзадач в одном PR — иначе ревью и откат отдельной
  части становятся неудобными.
- Ветки от `main`, имя вида `<номер-этапа>-<короткое-описание>`, например
  `1.3-my-chat-member`, `2.4-rsvp-callback` (номер соответствует пункту
  `docs/TASKS.md`).
- Перед открытием PR обязаны проходить локально: `uv run ruff check .`,
  `uv run mypy src`, `uv run pytest` — тот же набор, что в CI
  (`.github/workflows/ci.yml`).
- В описании PR — что сделано и какой пункт `docs/TASKS.md` закрывает.
  После мержа отмечать пункт в `docs/TASKS.md` как выполненный в этом же PR
  (чекбокс `- [x]`).
- Не начинать следующую подзадачу, пока предыдущий PR не смержен, если явно
  не оговорено иное — так проще ревьюить и держать контекст.
- Не пушить в `main` и не мержить PR без явного запроса пользователя — только
  создание ветки/коммитов/PR на ревью.

## Источники правды

- [`docs/CONCEPT.md`](./docs/CONCEPT.md) — что и зачем (фичи, скоуп MVP/backlog).
- [`docs/TZ.md`](./docs/TZ.md) — как (стек, модель данных, архитектура, разделы
  1–6); раздел 7 — укрупнённый roadmap по этапам.
- [`docs/TASKS.md`](./docs/TASKS.md) — тот же roadmap, разбитый на PR-размерные
  подзадачи с ссылками на конкретные разделы `TZ.md`. Использовать его как
  чек-лист прогресса, `TZ.md` — как источник деталей реализации по каждому
  пункту.

Новых фич сверх `CONCEPT.md`/`TZ.md` не вводить без явного запроса — при
необходимости уточнить у пользователя, а не расширять скоуп самостоятельно.
